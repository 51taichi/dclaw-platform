# 超级专家 AIGC 工作流与执行向导设计

## 目标

DClaw 为正式授权的超级专家提供完整、通用、受控的 AIGC 工作流能力。超级专家负责表达制作意图和工作流结构，DClaw 负责校验、编译并原子创建真实画布；客户负责触发会产生费用的生成动作和确认结果，右侧向导按照真实节点状态逐步带客户完成。

产品定义固定为：

> DClaw 帮客户搭好工作流，向导带客户逐节点完成生成。

若某个节点在当前 DClaw 版本中无法自动搭建，但客户可以通过已有界面手动创建，则进入显式的手动兜底模式。手动兜底画布必须为空，向导才允许从创建节点开始，禁止在已搭建节点的画布上继续展示从零教学。

## “完整清单能力”的范围

本设计中的完整清单能力包含以下闭环，而不是只返回一份说明文字：

1. 发现当前租户可用的 AIGC 模型、工具、节点类型和参数约束；
2. 接收版本化的语义工作流蓝图；
3. 校验节点、模型、参数、连线、执行依赖和最终输出；
4. 原子创建单节点或多节点真实画布并返回稳定绑定；
5. 生成与实际工作流一致的逐节点执行清单；
6. 根据画布和任务状态自动判断当前步骤、完成、失败和恢复动作；
7. 将客户定位到当前节点和当前生成按钮；
8. 客户触发生成后跟踪排队、运行、成功或失败；
9. 多节点按依赖顺序解锁，最终产物绑定原任务并提交专家审核；
10. 自动搭建不可用时创建空白画布并切换到明确的手动搭建清单；
11. 刷新、离开页面或换设备后从服务端权威进度恢复；
12. 保持现有 v1 单节点任务和已创建任务可继续使用。

“完整”描述的是从能力发现、工作流创建、逐节点执行、恢复到最终提交的产品闭环。它不等于把尚无运行接口的实验节点伪装成可自动执行节点。DClaw 必须发现并报告当前节点注册表中的全部类型，同时为每一种类型明确返回 `AUTO_PROVISIONABLE`、`MANUAL_ONLY` 或 `UNAVAILABLE`；超级专家只能自动编排第一类节点。这样清单能力本身是完整的，实际执行范围又与当前 DClaw 真实能力一致。

本次不包含自动发布内容、替客户绕过费用确认、任意浏览器控制、向超级专家开放 DClaw 原始画布内部字段，或让超级专家直接执行未授权插件代码。

## 现状与根因

DClaw 的 AIGC 画布模型已经支持 `nodes`、`edges` 和多类生成节点，普通画布接口也能保存多节点图。但超级专家平台目前存在以下限制：

- `aigc.task.create/2` 只接受 `aigc.text_to_video.create`；
- `provision_super_expert_aigc_workspace` 只创建一个 `video_generate` 节点；
- 任务绑定只有一个 `node_id`；
- 操作契约的 `machine_executor` 固定为空；
- `human_guide` 是从空白画布出发的静态九步说明；
- 前端用本地 `localStorage` 保存当前步骤，而不是读取服务端权威进度；
- 当前向导在系统已创建项目、节点和参数后，仍要求客户再次创建和填写。

因此当前系统同时呈现“系统代建”和“从零教学”两套互相冲突的流程。

## 方案选择

### 方案 A：超级专家直接提交原始画布 JSON

实现速度快，但会暴露并固化前端 `node.data`、节点尺寸、预览状态和内部字段。前端一旦升级，已发布 Agent 的工作流可能失效，也难以安全过滤任意字段。本方案不采用。

### 方案 B：只允许超级专家选择 DClaw 内置模板

安全、简单，但无法覆盖不同业务生成的动态复杂工作流。每新增组合都要修改 DClaw 模板库，平台会重新理解具体 Agent 业务。本方案仅作为优化手段，不作为唯一接口。

### 方案 C：版本化语义蓝图，由 DClaw 编译为真实画布

超级专家只提交闭集的节点意图、依赖和制作参数；DClaw 根据当前节点实现生成原始画布数据。这样既支持动态多节点，也保持平台安全和前后端解耦。本设计采用方案 C，并允许语义蓝图引用 DClaw 内置模板作为快捷方式。

## 职责边界

### 超级专家负责

- 根据自身业务阶段确定素材目标；
- 从 DClaw 返回的能力清单中选择可用能力和模型；
- 形成语义工作流蓝图；
- 为每个节点提供业务标题、输入意图和生成参数；
- 指定依赖关系和唯一最终输出节点；
- 在客户提交成品后执行自己的业务审核。

### DClaw 服务端负责

- 鉴权、授权、租户和安装绑定；
- 返回当前真实能力清单；
- 校验并编译语义蓝图；
- 原子创建或回滚画布、节点、边和任务绑定；
- 维护工作流实例、步骤状态和事件；
- 将 AIGC Job 状态投影为向导进度；
- 绑定最终资产并调用原超级专家审核能力；
- 保持计费、幂等、审计和旧协议兼容。

### DClaw 前端负责

- 渲染预建工作流；
- 显示服务端给出的当前执行步骤；
- 定位目标节点和节点内生成控件；
- 由客户点击触发已有 Job 创建和运行；
- 展示运行状态、恢复动作和最终提交动作；
- 在手动兜底模式下按服务端清单协助客户搭建空白画布。

### 客户负责

- 对会产生积分消耗的生成动作进行点击确认；
- 检查节点生成结果；
- 选择重试、接受结果或返回陆羽调整方案；
- 提交最终产物给陆羽审核。

## 超级专家能力协议 v2

新增能力 `aigc.workflow.create/1`，保留现有 `aigc.task.create/2`。

这里的“v2”指超级专家 AIGC 产品能力的第二代协议；`aigc.workflow.create/1` 末尾的 `/1` 是该新命令自身的首个合同版本，两者不是同一个版本号。

### 模型输出与机器接口边界

语义蓝图是陆羽运行时适配层提交给 DClaw 的受类型约束机器请求，不是要求大模型直接输出的复杂 JSON。大模型仍按陆羽已经采用的容错文本/INI 返回格式表达制作意图；陆羽的确定性适配器负责解析、补全版本字段、从能力清单绑定稳定 ID、生成 API 请求并在本地做 Schema 校验。解析失败时不得猜测或把原始模型文本直接透传给 DClaw。

DClaw 对外机器接口继续使用标准 JSON/HTTP，这是服务间合同，不属于大模型返回格式，因而不会重新引入“一个标点导致整轮模型输出作废”的问题。

请求由三部分组成：

- `scope`：沿用安装、会话、Agent 任务、内容 revision 和素材任务绑定；
- `workflow`：版本化语义蓝图；
- `event_id`：唯一事件和幂等绑定。

语义蓝图包含：

- `schema_version`：首版为 `1`；
- `title`：客户可见的项目名称；
- `execution_preference`：首版只允许 `CUSTOMER_TRIGGERED`；
- `nodes`：有序语义节点列表；
- `edges`：节点依赖关系；
- `output_node_id`：唯一最终成品节点；
- `fallback_policy`：只允许 `MANUAL_BUILD_IF_UNSUPPORTED` 或 `FAIL_CLOSED`。

每个语义节点包含：

- `node_id`：蓝图内稳定逻辑标识，不是物理画布 ID；
- `kind`：DClaw 注册表中的闭集节点类型；
- `title`：客户可读名称；
- `capability`：该节点需要的生成能力，纯工作流节点可为空；
- `provider_id` 与 `model_id`：生成节点必须来自本轮能力清单；
- `inputs`：闭集语义输入，例如提示词、脚本、引用资产或上游输出；
- `parameters`：由节点能力 Schema 验证的参数；
- `customer_action`：首版生成节点固定为 `CLICK_GENERATE`；
- `optional`：是否允许跳过。

每条边只包含逻辑源节点、目标节点和受支持的输入槽位。DClaw 拒绝不存在的节点、重复逻辑 ID、自环、不支持的槽位和循环依赖。

超级专家不能提交物理 `canvas_id`、物理节点 ID、CSS 定位、React 组件名、任意 `node.data`、脚本或凭据。

### 首版节点注册表

DClaw 以服务端注册表作为节点能力的唯一权威源，前端节点菜单不能反向决定超级专家权限。首版必须覆盖当前 AIGC 画布已登记的全部节点类型，并如实标记状态：

- 自动预建且有真实执行/完成判定：`prompt`、`image_generate`、`video_generate`、`audio_generate`、`script_generate`、`long_image_export`；
- 自动预建但不产生模型 Job：`reference_note`、`output`；
- 有既有可信资产 ID 时可自动预建、否则需要客户上传：`reference_asset`；
- 当前只有前端实验能力、缺少稳定服务端执行合同：`video_compose`、`director_stage`，首版返回 `MANUAL_ONLY` 或 `UNAVAILABLE`，不得声称已自动执行。

节点注册表为每类节点定义语义输入 Schema、物理节点工厂、允许的输入槽位、输出类型、完成判定、稳定控件 ID、自动搭建状态和手动兜底条件。新增节点只通过扩展注册表和对应测试进入能力清单，不修改超级专家的通用工作流协议。

## 能力清单升级

保留现有 `aigc.capabilities.list/1` 的响应不变，新增独立的 `aigc.workflow.capabilities.list/1`，避免给旧调用方增加不认识的嵌套结构。新清单返回内容必须足够让超级专家构造合法蓝图：

- 稳定语义节点类型；
- 所支持的生成能力；
- 可选模型和供应商；
- 参数 Schema；
- 输入槽位和允许的上游输出类型；
- 输出资产类型；
- 是否支持自动搭建；
- 不支持自动搭建时是 `MANUAL_ONLY` 还是 `UNAVAILABLE`，以及稳定原因码；
- 是否需要客户触发；
- 当前价格目录中是否可用。

模型未发布、未定价、未授权或不可用时不得出现在可执行清单中。清单只描述平台事实，不包含陆羽业务阶段。

## 工作流编译与原子创建

DClaw 增加独立的工作流编译器，过程固定为：

1. 验证安装授权、租户、会话和内容 revision；
2. 校验蓝图 Schema 和大小上限；
3. 校验节点类型、模型、参数和输入输出兼容；
4. 校验图为有效有向无环图并存在唯一最终输出；
5. 为每个逻辑节点生成物理节点 ID；
6. 使用 DClaw 自己的节点工厂生成稳定 `node.data`；
7. 计算不重叠的初始布局和可见 viewport；
8. 生成物理连线和逻辑到物理绑定；
9. 生成实例化执行清单；
10. 原子写入画布、任务和创建事件。

任一步失败都不得留下半个画布、孤立任务或部分绑定。重复相同幂等请求返回同一工作流；相同幂等键对应不同蓝图时拒绝。

首版设置可配置上限，默认每个工作流最多 20 个节点、40 条边、一个最终输出节点。该上限用于保护稳定性，不限制未来协议扩展。

## 任务绑定与兼容

v2 任务绑定新增：

- `workflow_id`；
- `execution_mode`：`PREBUILT_WORKFLOW` 或 `MANUAL_BUILD`；
- `node_bindings`：逻辑节点 ID 到物理节点 ID 的有序映射；
- `output_node_id`：物理最终输出节点；
- `workflow_revision`；
- `guide_revision`。

现有 `binding.node_id` 保留，并始终投影为物理最终输出节点，使旧客户端和现有提交审核路径继续工作。已创建的 v1 单节点任务不迁移数据，前端使用旧向导兼容渲染。

## 实例化执行清单

v2 清单属于具体任务实例，不再只来自静态操作手册。每一步包含：

- `step_id`；
- `kind`：`INSPECT`、`GENERATE`、`WAIT`、`VERIFY`、`SUBMIT` 或手动搭建动作；
- `title` 和简短说明；
- `logical_node_id` 与物理 `node_id`；
- `control_id`；
- `status`：`LOCKED`、`READY`、`RUNNING`、`COMPLETED`、`FAILED`、`SKIPPED`；
- `completion_rule`；
- `recovery`；
- `blocking_reason`。

预建工作流的正常步骤只包含：

1. 检查当前节点已经预填的目标和参数；
2. 点击当前节点生成按钮；
3. 等待生成完成；
4. 检查结果，必要时重试；
5. 自动定位并解锁下一个节点；
6. 最终节点完成后由客户点击“完成并返回会话”，平台校验素材归属后直接完成任务。

不得再展示“新建项目、添加节点、粘贴提示词、选择模型”等已由平台完成的步骤。

步骤状态由服务端根据画布、Job、资产和任务事件推导并持久化。前端 `localStorage` 只允许保存面板展开状态等展示偏好，不能作为权威步骤进度。

服务端持久化步骤定义、客户显式接受/重试/跳过事件和工作流 revision；`READY`、`RUNNING`、`COMPLETED`、`FAILED` 等运行状态由这些记录与当前 Job/资产事实确定性投影。不得由前端直接提交“已完成”覆盖真实 Job 状态。

必需生成节点在 Job 成功且产生合格输出后自动完成并解锁下游，客户不需要再点击一遍“确认完成”。重试继续使用节点自己的真实重试/生成入口。只有蓝图声明为 `optional=true` 的节点才显示“跳过此步骤”；跳过动作通过现有 `aigc.guide.update` 能力写入绑定任务的不可变向导事件，并同时校验 `workflow_id`、`guide_revision`、`step_id` 和物理节点绑定。旧单节点任务继续保留原 `aigc.guide.update` 兼容行为。

## 手动兜底模式

只有同时满足以下条件才允许手动兜底：

- 蓝图请求明确允许兜底；
- 所需能力已授权；
- 当前前端能够手动创建该节点；
- 自动编译失败原因属于“当前节点不支持自动搭建”，而不是鉴权、计费、模型不可用、参数错误或内部错误。

DClaw 在兜底模式创建绑定任务和空白画布，不创建任何业务节点或连线。任务返回 `execution_mode=MANUAL_BUILD` 和明确原因，向导从创建节点开始。

鉴权失败、模型未发布、价格不可用、非法参数、循环依赖、越权节点、存储失败等情况必须关闭失败，不能用手动兜底掩盖。

## 向导界面

右侧面板重新建立以下视觉层级：

1. 固定头部显示“执行向导”、当前步骤和总步骤；
2. 任务名称保留一行；
3. 模型、比例、时长以紧凑标签展示；
4. 完整提示词和详细制作参数默认折叠为“查看任务参数”；
5. 当前步骤卡片占据主体，包含当前动作、目标节点、状态和主要按钮；
6. 当前步骤下面只显示完成条件和遇到问题时的恢复动作；
7. 已完成步骤折叠，下一步只做简短预告；
8. 底部固定“暂停向导”和当前主操作。

当当前步骤为生成时，主按钮为“定位到节点”，画布中的真实生成按钮同时高亮。客户必须点击节点内真实生成按钮，向导不能伪造第二套生成入口。

任务参数是参考信息，不再作为页面主区域。当前步骤是唯一视觉主任务。

## 画布底部工具栏

缩放和小地图工具栏从页面右下角移动到有效画布区域的水平中心、底部 24 像素位置。

有效画布区域不包含全局左侧导航和展开的右侧向导。实现上由 AIGC 画布容器提供定位上下文，工具栏使用绝对定位，不再相对整个浏览器窗口固定。向导展开、收起和窗口缩放时，工具栏均重新居中。

小地图面板相对工具栏向上展开，不能遮挡右侧向导或当前节点操作区。

## 节点定位与控件协议

每个可执行节点和生成按钮必须具有稳定平台标识：

- 节点容器：物理 `node_id`；
- 生成按钮：节点实例内稳定 `control_id`；
- 重试、查看结果等动作使用同一注册表。

向导定位时先把节点移动到有效画布区域中心，再聚焦节点内目标控件。控件不存在、节点被删除或画布绑定不一致时立即阻断，不猜测其他控件。

## 状态、事件与恢复

新客户完成路径：

`WAITING_TO_START → IN_PROGRESS → ACCEPTED`

旧专家的 `SUBMITTED → REVIEWING → ACCEPTED/REVISION_REQUIRED` 状态和能力继续兼容读取与处理，但新任务页不再触发模型审核。

工作流实例另行维护节点和步骤状态。第一个生成步骤准备好后任务进入 `IN_PROGRESS`。Job 的 queued、running、succeeded、failed 和 cancelled 事件更新对应步骤；只有所有必需上游步骤完成后，下游 `GENERATE` 才变为 `READY`。

页面刷新时依次读取任务、工作流实例、画布和 Job 状态，重新计算当前步骤。Redis 或浏览器事件只负责加速刷新，不是唯一事实来源。事件丢失后仍能从持久化数据恢复。

节点输出被重新生成时，所有依赖旧输出的下游完成状态失效并回到待执行状态。工作流 revision 变化后旧清单回执失效。

## 计费与客户确认

创建工作流、节点、连线和预填参数不产生模型费用。所有可能产生费用的 AIGC Job 继续使用 DClaw 现有计费入口。

v2 首版禁止超级专家自动点击或批量执行生成。客户点击真实生成按钮后，DClaw 才创建用量订单并执行。未来若增加自动执行，必须使用新的合同版本和独立的一次性预算授权，不能通过升级本协议偷偷启用。

## 安全约束

- 只有正式签名、已安装且整体授权的超级专家可以调用工作流能力；
- 蓝图只接受闭集语义字段，拒绝额外字段；
- 节点类型、能力、模型和参数均按当前租户能力清单验证；
- 所有物理 ID 由 DClaw 生成；
- 任务、画布、节点、Job 和资产必须属于同一用户与会话；
- 超级专家不能提交任意路径、URL、HTML、脚本、凭据或原始节点数据；
- 读兼容入口保持只读，写命令继续使用受保护的用户 API；
- 最终素材通过不等于内容发布审核通过，陆羽 S0-S15 Gate 不变。

## 陆羽接入

陆羽增加通用工作流蓝图适配，但不把 DClaw 节点实现写入业务 Skill。

执行流程为：

1. 陆羽在原业务阶段确定内容任务和制作目标；
2. 查询 DClaw 工作流能力清单；
3. 按当前内容生产计划生成语义蓝图；
4. 调用 `aigc.workflow.create/1`；
5. 回复客户工作流已经搭好，请进入任务卡片逐节点生成；
6. 接收最终素材并沿原 S8、S10、S11 审核链继续。

简单任务可以提交只有一个节点的蓝图，复杂任务可以提交多个节点和连线。是否复杂由陆羽业务 Skill 决定；DClaw 只验证平台可执行性，不理解 S0-S15。

陆羽发布包需要升级版本，并声明新能力。旧陆羽发布版本继续使用 `aigc.task.create/2`。

## 错误处理

工作流创建返回稳定错误分类：

- `WORKFLOW_SCHEMA_INVALID`；
- `NODE_KIND_UNSUPPORTED`；
- `MODEL_UNAVAILABLE`；
- `PARAMETER_INVALID`；
- `EDGE_INCOMPATIBLE`；
- `WORKFLOW_CYCLE`；
- `OUTPUT_NODE_INVALID`；
- `MANUAL_BUILD_REQUIRED`；
- `WORKFLOW_CONFLICT`；
- `PROVISIONING_FAILED`。

客户界面显示可执行的恢复动作，不暴露内部路径、堆栈或供应商密钥。可安全重试的创建请求复用原幂等键；蓝图修改后必须使用新的内容 revision 和新幂等键。

## 测试与验收

### DClaw 服务端

1. 能力清单覆盖当前注册表全部节点，并准确描述每类节点的自动搭建状态、槽位和参数；
2. 合法单节点蓝图创建真实画布、节点、任务和清单；
3. 合法三节点蓝图创建全部节点、连线和逻辑到物理绑定；
4. 输出节点继续投影到旧 `binding.node_id`；
5. 非法模型、参数、边、循环、重复 ID 和多输出均在写入前失败；
6. 任意写入失败不留下部分画布或任务；
7. 幂等重放返回同一绑定，不重复创建；
8. 手动兜底只针对受支持的不可自动搭建节点，并创建空白画布；
9. Job 事件推进对应步骤并按依赖解锁下游；
10. 上游重新生成使相关下游步骤失效；
11. 刷新恢复不依赖运行时事件缓存；
12. 越权用户、普通 Agent 和未授权超级专家均无法读取或执行任务；
13. v1 单节点创建、向导、提交和审核回归保持通过。

### DClaw 前端

1. 预建模式不出现创建项目、添加节点或填写已预填参数的步骤；
2. 手动模式打开的是空白画布，并显示搭建步骤；
3. 参数摘要紧凑，完整参数默认折叠；
4. 当前步骤是面板唯一主视觉区域；
5. 定位动作选中正确节点并聚焦真实生成按钮；
6. 节点运行状态自动更新当前步骤；
7. 刷新和换设备从服务端恢复同一步骤；
8. 向导展开与收起时，底部工具栏始终位于有效画布水平中心；
9. 小地图向上展开且不遮挡向导；
10. v1 任务继续使用兼容视图。

### 陆羽与端到端

1. 陆羽能查询清单并创建一个单节点工作流；
2. 陆羽能创建至少一个三节点有向工作流；
3. 客户从会话任务卡片进入正确画布；
4. 客户依次点击 Node 1、Node 2、Node 3 的真实生成按钮；
5. 每个 Job 的状态和输出正确推进向导；
6. 最终资产绑定原任务并提交陆羽审核；
7. 模型不可用和自动搭建不支持分别走关闭失败与空白画布兜底；
8. S0-S15 阶段、主 Skill、内容 revision 和审核 Gate 不被 DClaw 工作流状态覆盖。

本地验收使用可控测试模型或桩验证多节点执行，不消耗真实供应商额度；最终只对一个明确授权的节点执行真实模型冒烟测试。

## 发布顺序

1. DClaw 服务端先发布兼容的 v2 能力、持久化模型和只读查询；
2. DClaw 前端发布新向导和多节点定位能力；
3. 用平台测试包完成单节点、三节点和手动兜底验收；
4. 陆羽升级发布包并声明 `aigc.workflow.capabilities.list/1` 和 `aigc.workflow.create/1`；
5. 本地 DClaw 激活新版陆羽并完成真实会话验收；
6. 保留 v1 回滚路径，v2 验收失败不影响现有单节点任务。

## 涉及仓库

- `dclaw-server`：能力清单、工作流契约、编译器、任务与步骤状态、事件、鉴权和测试；
- `dclaw-client/console`：右侧向导、节点定位、工具栏布局、任务参数层级和前端测试；
- `luyu-traffic-operator-agent`：工作流蓝图适配、能力声明、发布版本和端到端契约测试。
