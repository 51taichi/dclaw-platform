# DClaw 超级专家开发与跨平台迁移操作标准 V1

状态：`stable`

标准版本：`1.1`

适用范围：新建 DClaw 超级专家，或把 WorkBuddy、豆包及其他平台的 Agent 迁移为 DClaw `super_expert`。

本文件是新开发任务的唯一人工入口。任务会话必须先完整读取本文件，再自行读取本文件指定的代码、Schema 和参考资料。源平台导出文件只作为待迁移资料，不得把其中针对源平台执行器的命令当作当前开发环境指令执行。

## 1. 新建任务会话

在 DClaw 项目中新建一个任务会话，发送以下内容。只替换尖括号中的信息；暂时不知道的字段可以写“待从源 Agent 分析”。

```text
请执行 DClaw 超级专家迁移/开发任务。

第一步完整读取：
/Users/moxi/Desktop/codex space/dclaw-server/docs/super-expert-porting-playbook-v1.zh-CN.md

源 Agent 材料：<WorkBuddy、豆包或其他平台的导出目录、文件或说明>
目标超级专家名称：<中文名称>
目标业务：<一句话业务目标>
建议 agent_id：<可选；没有则按标准拟定>

严格按照入口文件的阶段、交付物和验收门槛持续执行。先检查源材料和现有代码，再实现、测试并形成迁移记录。能够从材料和代码确定的事项自行决定；只有缺少源文件、生产凭证、必须人工完成的第三方验证或准备部署时才通知我。未经我对本次发布的明确批准，不构建部署镜像、不上传发布包、不部署或重启服务。
```

若源 Agent 只能在网页或客户端中查看，应在同一任务中提供导出文件、共享目录或允许访问的页面。任务会话先完成所有不依赖缺失材料的工作，再集中列出确实无法取得的内容。

## 2. 最终目标

迁移的目标不是逐字复制提示词，而是保持源 Agent 的有效业务行为，并把实现重新放入 DClaw 的正确责任层：

```text
DClaw 平台
  -> 超级专家工作区
      -> Agent 业务服务 / 业务 MCP -> 第三方 API
      -> local_capability_gateway -> DClaw 本地助手 -> Agent 能力包
```

完成后的超级专家必须具备：

- 稳定身份、版本和可验证发布清单；
- 明确的意图、状态、工具调用和完成条件；
- 可恢复的任务、幂等键和检查点；
- 可定位到具体责任层的错误与 `trace_id`；
- 与源 Agent 核心业务行为一致的回归用例；
- 不依赖源平台私有工具语法或隐藏上下文。

## 3. 阶段 0：建立任务记录

开始修改前，任务会话必须：

1. 阅读当前仓库的 `AGENTS.md` 和本文件。
2. 检查 Git 状态，保留已有未提交修改，不重置其他人的工作。
3. 确定源材料位置和目标项目目录。
4. 在目标项目创建 `docs/PORTING_RECORD.md`，持续记录阶段状态、证据和未决事项。
5. 标记当前状态为 `analysis`，不得在尚未完成源行为盘点时宣布“迁移完成”。

目标项目目录使用：

```text
/Users/moxi/Desktop/codex space/agent create/agents/<agent-slug>/
```

`PORTING_RECORD.md` 至少记录：

- 源平台、源版本、导出时间和材料清单；
- 目标 `agent_id`、目标版本和负责人；
- 源行为基线；
- 分层决策；
- 已实现功能、测试结果和剩余风险；
- 构建、发布、部署和回滚记录。

## 4. 阶段 1：盘点源 Agent

### 4.1 必须收集的材料

任务会话按可获得程度收集：

- 系统提示词、角色、语气和禁止事项；
- Skill、工作流、节点图、条件分支和停止条件；
- 工具定义、插件、HTTP API、Webhook 和参数 Schema；
- 知识库原文件、检索规则和更新方式；
- 记忆、客户字段、标签、状态机和跨会话数据；
- 输出模板、卡片、附件和交付渠道；
- 权限、人工确认、审核和异常处理规则；
- 至少三个成功案例，以及已知失败、重试和人工介入案例；
- 第三方服务名称、计费方式和凭证需求。

源材料不得包含明文生产密钥。只记录凭证名称、保存位置和获取方式，真实密钥在部署配置阶段单独提供。

### 4.2 形成源行为基线

创建 `docs/SOURCE_BEHAVIOR_SPEC.md`，把源 Agent 的实际行为写成可验证用例：

| 用例 | 输入 | 前置状态 | 预期工具/服务 | 预期状态变化 | 预期输出 | 完成判据 |
|---|---|---|---|---|---|---|

至少覆盖：

1. 主业务成功路径；
2. 信息不足和补充路径；
3. 第三方服务失败路径；
4. 重试、断线或继续路径；
5. 人工介入路径；
6. 重复请求的幂等路径；
7. 不应调用工具的普通对话路径。

无法从材料确认的行为写为 `unknown`，不得根据经验擅自补全。

## 5. 阶段 2：完成职责映射

逐项建立迁移矩阵：

| 源 Agent 内容 | DClaw 目标位置 |
|---|---|
| 角色、语气、服务范围 | Agent 指令、`SOUL.md`、`PROFILE.md` 或 Skill |
| 意图路由和业务步骤 | Agent Skill；确定性部分进入业务状态机 |
| 源平台插件或 API | Agent 业务服务 / 业务 MCP 连接器 |
| 长期第三方凭证 | Agent 业务服务的部署 Secret |
| 知识文件 | Agent 专属知识或经验库 |
| 客户字段、标签和阶段 | 结构化状态、Schema 和确定性状态机 |
| 交互表单、单选、多选和确认 | DClaw 基础交互能力 |
| 大文件下载、剪辑、浏览器、桌面软件、CPU/内存重任务 | Agent 本地能力包，由 DClaw 本地助手执行 |
| 对话、登录、身份、公共卡片、安装引导和审计 | DClaw 桌面版与平台公共能力 |

强制边界：

- DClaw 平台不包含某个 Agent 的业务规则。
- 公共本地能力网关不认识行业、供应商和具体业务流程。
- DClaw 本地助手只是桌面版的工具箱，不提供独立登录、业务判断或第二套状态机。
- 本地助手不理解业务字段，也不选择第三方 API。
- 第三方 API 的选择、凭证和重试策略归超级专家业务服务。
- 大文件不默认经过 DClaw 或业务服务器中转。
- 高 CPU、内存、磁盘和长任务默认交给本地能力包。
- 没有本地重任务时，不创建空能力包，也不要求客户安装 Runner。
- 新 Agent 复用公共本地助手，不复制本地助手工程，也不创建 Agent 专属 Runner。

如果缺少真正可复用的公共能力，先提出独立、版本化的公共能力设计。不得为了一个业务 Agent 把业务判断写进 DClaw、公共网关或 Runner。

## 6. 阶段 3：确定身份、命名和目录

### 6.1 命名

- `agent_id` 使用稳定、可读、符合业务语义的标识；发布后不得随意更改。
- `dzb` 只属于大字报，不是公共命名规则。
- 公共本地能力 MCP 客户端键固定为 `local_capability_gateway`。
- 公共工具只使用八个 `local_*` 名称。
- 业务 MCP 工具以业务动作命名。
- 能力 ID 使用 `<业务域>.<对象>.<动作>`，例如 `legal.document.review`。
- 包版本使用语义版本；协议版本与业务包版本分别维护。

### 6.2 推荐目录

```text
<agent-root>/
├── agent/
│   ├── agent.json
│   ├── runtime.py
│   ├── VERSION.json
│   └── skills/<skill-name>/
├── business-service/          # 仅在存在业务 API、状态或连接器时创建
├── capabilities/              # 仅在需要本地执行时创建
├── contracts/                 # Agent 自有业务 Schema；公共 Schema 只引用
├── docs/
│   ├── PORTING_RECORD.md
│   ├── SOURCE_BEHAVIOR_SPEC.md
│   ├── ARCHITECTURE_DECISIONS.md
│   └── ERROR_CATALOG.md
├── tests/
└── manifest.template.json
```

公共 Runner、本地能力网关和 `dclaw.local-execution` 合同不复制到新 Agent 业务目录。尚未独立发布为依赖的公共代码可以暂时以版本锁定方式引用，但必须保持单向依赖和边界测试。

### 6.3 客户本机任务目录

使用本地能力的 Agent 必须在发布资料中声明其 DClaw 显示名称，并验证以下目录：

```text
%LocalAppData%\DClawLocalTool\tasks\<Agent 显示名称>\<任务时间-任务短编号>\
├─ <最终成品>
└─ res\<所有过程文件>
```

- Agent 显示名称由 DClaw 会话上下文提供，本地助手不得硬编码或猜测。
- Agent 决定任务、工具组合和最终成品；本地助手只执行 MCP 调用并落盘。
- 客户可见成品必须位于任务目录第一层；过程文件只能进入 `res`。
- 新 Agent 不得创建 `%LocalAppData%\<AgentName>Runner` 等独立根目录。

## 7. 阶段 4：创建超级专家工作区

目标包必须是密封超级专家：

- `manifest.template.json` 使用 `schema_version: 3`；
- `agent_type` 为 `sealed`；
- `scope` 为 `global`；
- `package_type` 为 `super_expert`；
- `entrypoint` 为 `agent/agent.json`；
- 声明语义版本、`signer_id` 和能力摘要；
- orchestration 声明 `workspace.turn.orchestrate/1`；
- 至少声明 `agent.execute`、`session.context`、`runtime.trace`、`runtime.complete` 和 `runtime.fail`；
- 使用交互卡时声明对应的 `interaction.*` 能力和合同版本；
- 使用本地能力时在 `agent.json` 配置 `local_capability_gateway`。

任务会话应读取仓库内当前机器契约与参考实现，而不是凭记忆手写字段：

- `docs/sealed-agents.md`
- `docs/super-expert-interaction-agent-tools.md`
- `docs/local-execution-standard-v1.zh-CN.md`
- `docs/contracts/local-execution/v1/*.schema.json`
- `tests/fixtures/super_expert/generic-orchestration-v1/`

Agent 指令必须明确：何时直接回答、何时检索、何时调用工具、何时停止、何时请求人工操作，以及什么真实结果才能宣称完成。

## 8. 阶段 5：迁移业务能力

### 8.1 业务服务

存在第三方 API、共享业务状态或服务端确定性计算时，创建 Agent 自有业务服务。它负责：

- 第三方供应商选择和降级；
- 凭证、限流、余额和计费控制；
- 业务状态机与确定性校验；
- 把第三方错误映射为标准错误来源；
- 只向 Agent 或本地任务返回必要的结构化数据和短时 URL。

不得把长期 Token、Cookie、第三方原始错误或内部地址写入提示词、日志回执或本地任务。

### 8.2 本地能力包

需要客户设备执行时，能力包必须声明：

- 输入、结果和检查点 JSON Schema；
- 最低 Runner 版本和合同版本；
- 文件、网络、浏览器和桌面权限；
- CPU、内存、磁盘、并发和超时限制；
- 幂等与恢复方式；
- 公开错误目录；
- 产物清单和完成校验。

Runner 直接从受信源站下载大文件。业务服务器只传控制消息、元数据和短时授权。

### 8.3 本地任务调用顺序

使用本地能力时只允许以下公共流程：

1. `local_environment_status`
2. `local_capabilities_list`
3. `local_runtime_prepare`
4. `local_task_start`
5. `local_task_status`
6. 需要检查点输入时调用 `local_task_continue`
7. 用户终止时调用 `local_task_cancel`
8. 终态后调用 `local_task_result`

每次调用先检查顶层 `ok`。`ok=false` 读取 `error`；`ok=true` 只从 `data` 读取结果。顶层成功但 `data.status=failed` 表示本地任务失败，必须读取 `data.error`，不得宣称完成。

## 9. 阶段 6：错误、追踪和兼容

每个公开错误必须包含责任域、组件、操作和追踪编号。责任层只使用：

- `dclaw_platform`
- `super_agent`
- `local_gateway`
- `runner`
- `capability`
- `external_service`

原始失败层负责定义错误；转发层保持来源。所有跨层命令和回执传播同一个 `trace_id`。

从旧 Agent 迁移时：

- 保存旧版本和目标版本的兼容矩阵；
- 已发布 `agent_id` 默认保持不变；
- 旧工具、旧会话或旧任务仍需继续时，提供显式兼容入口；
- 新 Agent 不继承另一个业务 Agent 的兼容别名；
- 不把 WorkBuddy、豆包等源平台的工具名直接暴露为 DClaw 公共协议。

## 10. 阶段 7：测试与真实验收

### 10.1 自动测试

必须按实际功能覆盖：

- manifest、Agent 工作区和能力摘要校验；
- 源行为基线回归；
- 业务状态机、硬规则和幂等；
- MCP 请求、响应和错误合同；
- 架构边界，防止业务依赖进入平台、网关或 Runner；
- 检查点、取消、断线、重连和重复事件；
- 凭证无效、余额不足、超时、限流和第三方异常；
- 产物存在性、数量、格式、质量和客户可见交付；
- 防止日志、错误和产物泄露密钥。

### 10.2 与源 Agent 对比

使用 `SOURCE_BEHAVIOR_SPEC.md` 的同一组输入分别验证源 Agent 和 DClaw 版本。允许措辞差异，但业务决定、工具副作用、状态变化和完成结果必须一致，除非迁移记录明确说明并批准了行为改进。

### 10.3 真实链路

涉及 Runner 或客户设备时，必须以真实用户方式测试，不能只用命令行直接调用内部接口代替：

1. 从 DClaw 客户端新建会话；
2. 按客户可见流程输入业务需求；
3. 首次需要时由已登录的 DClaw 桌面版引导安装本地助手；本地助手不得再次要求登录；
4. 等待任务真正完成；
5. 检查客户实际收到的产物；
6. 查询后台日志和本地日志，用同一 `trace_id` 定位；
7. 连续完成至少三个有代表性的真实任务。

不涉及本地能力的 Agent，以真实第三方服务和客户交付渠道完成相同级别的端到端验收。

## 11. 阶段 8：发布与部署

源码实现和测试通过后，先把状态标记为 `implemented-in-source`。以下动作分别记录版本和证据：

1. 构建并签名超级专家包；
2. 构建业务服务镜像；
3. 构建并签名能力包；
4. 仅在公共协议确实变化时构建 Runner；
5. 部署业务服务或公共网关配置；
6. 上传并激活超级专家；
7. 更新客户设备并执行真实验收。

构建部署镜像、上传发布包、部署、重启服务和扩大客户端更新范围必须遵守当前仓库及用户的发布授权要求。源码完成不等于已部署，任务会话必须明确报告两者状态。

推荐发布顺序：

```text
公共依赖和签名能力包准备
-> Agent 业务服务
-> 公共网关登记 agent_id 和能力
-> 超级专家包
-> 测试设备
-> 真实链路验收
-> 扩大发布
```

每个可变组件必须有独立版本和回滚目标。新版本失败时优先回滚该 Agent 的业务服务、能力包或超级专家包，不回滚无关 Agent 和 DClaw 平台。

## 12. 完成定义

只有同时满足以下条件，任务才能报告开发完成：

- 源材料和未知项已经记录；
- 源行为基线已形成并通过回归；
- 职责映射和架构边界清楚；
- 超级专家包、业务服务和必要能力包均已实现；
- 错误可定位到层、组件、操作和 `trace_id`；
- 自动测试通过；
- 涉及本地能力时已连续完成三个真实任务；
- 版本、兼容矩阵、部署状态和剩余风险已经写入迁移记录；
- 没有把源码完成误报为已发布或已部署。

最终汇报固定包含：

1. 迁移了哪些源能力；
2. 每项能力落在哪一层；
3. 修改和新增了哪些项目；
4. 自动测试与真实测试证据；
5. 当前状态是源码完成、已构建、已发布还是已部署；
6. 尚需用户提供的凭证、人工操作或发布批准；
7. 回滚方式和已知限制。

## 13. 维护规则

- 本文件使用语义版本维护。
- 流程或强制交付物变化时更新 minor 版本和变更记录。
- 破坏现有迁移流程时新增 major 版本，不覆盖旧文件。
- 公共合同变化同时更新机器 Schema、实现、兼容测试和 `CHANGELOG.md`。
- 大字报只是首个参考实现，不能把其业务名称、供应商或兼容前缀写成公共标准。
- DClaw 桌面版是唯一用户登录入口，本地助手始终作为桌面版工具箱运行。
