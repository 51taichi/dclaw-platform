# 组织共享积分与成员额度设计

**日期：** 2026-10-21

**状态：** 设计草案，暂缓实施

**涉及仓库：** `dclaw-server`、`dclaw-client/console`

## 1. 背景与目标

DClaw 当前以用户作为身份、权限和计费主体，每个用户拥有独立积分钱包，平台管理员可以管理用户并查看全局积分与 Token 消耗。

未来需要增加“组织”概念，用于表示公司或团队：

- 用户可以不属于任何组织，也可以属于一个组织；默认不属于组织。
- 无组织用户继续使用个人积分钱包，现有功能和数据保持不变。
- 组织成员共同消费一个组织积分钱包。
- 平台管理员负责创建、编辑、停用组织以及指定组织管理员。
- 平台管理员不负责组织普通成员、成员额度和组织内部消费管理。
- 组织管理员负责管理本组织成员、分配成员消费额度，并查看周期内各成员的积分和 Token 消耗。
- 组织管理员登录客户端后，在工作台侧边栏看到“成员 / Token 消耗”入口；普通成员和无组织用户看不到该入口。

本设计只定义后续实现边界和安全约束。本阶段不新增数据库表、API、权限或客户端菜单，不改变任何线上计费行为。

## 2. 设计原则

### 2.1 向后兼容

- 所有现有用户在迁移后均保持无组织状态。
- 不迁移、不合并、不清空现有个人钱包和账本。
- 无组织用户的登录、充值、扣费、余额提醒和报表必须与当前行为一致。
- 新字段和新关系必须可空，服务端先兼容旧客户端，客户端再使用新增能力。

### 2.2 组织身份与全局角色分离

现有 `users.role` 继续只表示平台级角色，例如 `admin` 和 `user`。组织管理员不是新的全局角色，使用组织成员关系上的 `is_admin` 表示。

这样可以避免组织管理员意外获得平台管理接口权限，也不会要求修改所有现有的 `role == "admin"` 判断。

### 2.3 共享余额与成员额度分离

组织积分只保存在一个组织钱包中。组织管理员给成员设置的是“消费额度”，不是把积分转入成员个人钱包。

- 组织钱包余额是资金上限。
- 成员额度是组织内部的消费上限。
- 一次消费必须同时满足组织可用余额和成员剩余额度。
- 实际预扣、结算和退款始终发生在组织钱包。
- 成员额度不形成新的积分资产，不可充值、转让或提现。

该模型能够保持“共享组织积分”的产品含义，并避免成员离开组织时发生复杂的积分回收和退款迁移。

## 3. 术语与权限边界

| 身份 | 可管理范围 | 明确禁止 |
| --- | --- | --- |
| 平台管理员 | 组织基本信息、组织状态、组织管理员任命 | 管理组织普通成员、设置成员额度、代替组织管理员查看或操作组织内部数据 |
| 组织管理员 | 本组织成员、成员额度、本组织成员消费报表 | 访问其他组织、平台管理能力、修改组织钱包账本 |
| 组织普通成员 | 使用组织能力并查看自己的消费信息 | 查看其他成员、修改额度、管理成员 |
| 无组织用户 | 继续使用个人钱包和现有功能 | 访问任何组织资源 |

“平台管理员不能管理组织成员”必须由服务端权限校验保证，不能只通过隐藏客户端按钮实现。

## 4. 数据模型

### 4.1 `organizations`

建议字段：

- `id`：稳定主键。
- `name`：组织名称。
- `status`：`active` 或 `disabled`。
- `created_by`、`created_at`、`updated_at`。

组织停用不删除历史数据。停用后的新消费策略需要在实施前确定，建议默认禁止新消费、允许查询历史和完成账务对账。

### 4.2 `organization_members`

建议字段：

- `organization_id`：所属组织。
- `user_id`：成员用户。
- `is_admin`：是否为组织管理员。
- `quota_mode`：`limited` 或 `unlimited`。
- `quota_credits`：当前周期额度，限额模式下非负。
- `quota_period_type`：额度周期类型。
- `joined_at`、`left_at`、`created_at`、`updated_at`。

关键约束：

- 活跃成员关系对 `user_id` 唯一，保证一个用户同时最多属于一个组织。
- 每个启用组织至少保留一名组织管理员，避免组织失去管理入口。
- 组织管理员本身也必须是该组织的成员。
- 成员关系不物理删除，使用离开时间或状态保留历史审计。

如果最终只需要当前关系而不需要任职历史，可将历史另存事件表；不建议仅在 `users` 表增加 `organization_id` 和 `organization_admin`，因为成员变更、审计和历史报表会变得脆弱。

### 4.3 组织钱包

复用现有 `billing_wallets`：

```text
owner_type = "organization"
owner_id   = organization.id
```

现有 `(owner_type, owner_id)` 唯一约束可以保证每个组织只有一个钱包。个人钱包继续使用：

```text
owner_type = "user"
owner_id   = user.id
```

### 4.4 成员周期额度

成员额度需要独立的周期状态，不能只在成员表保存一个累计值。建议增加周期记录，例如 `organization_member_quota_periods`：

- `organization_id`、`user_id`。
- `period_start`、`period_end`。
- `quota_credits`、`held_credits`、`consumed_credits`、`released_credits`。
- `version` 或其他并发控制字段。

额度预占和组织钱包预占必须在同一个数据库事务内完成。余额充足但额度不足，或额度充足但余额不足，都不能向供应商发起可计费工作。

### 4.5 历史归属快照

消费订单或执行记录必须固化消费发生时的：

- `payer_user_id`。
- `billing_owner_type`、`billing_owner_id`。
- `organization_id`，无组织时为空。
- 成员额度周期标识。

报表不得使用用户“当前所属组织”反推历史归属。用户退出或更换组织后，原消费仍属于发生时的组织。

## 5. 计费主体解析

所有计费入口必须统一调用服务端的计费主体解析器，不允许在页面或单个业务模块内自行判断：

```text
resolve_billing_principal(user_id, operation_started_at)

无活跃组织成员关系
  -> 个人钱包

有活跃组织成员关系
  -> 组织钱包 + 成员身份 + 当前额度周期
```

解析结果必须在创建消费订单时持久化。任务重试、暂停后继续、结算、退款和对账均复用原始结果，不能再次按用户当前组织解析。

需要覆盖的入口至少包括：

- 工作台和普通对话。
- 专家、超级专家和专家团。
- AIGC 图片、视频、音频等能力。
- Open API。
- 自动化、定时任务和后台任务。
- 外部渠道和后续新增的计费入口。

## 6. 预扣、结算与退款

### 6.1 创建预扣

组织成员发起消费时，在同一个锁定事务内：

1. 读取并锁定组织钱包。
2. 读取并锁定成员当前额度周期。
3. 校验组织状态、成员状态、组织余额和成员剩余额度。
4. 在组织钱包创建预扣。
5. 在成员额度周期增加 `held_credits`。
6. 写入不可变的订单归属快照。

任一步失败都必须整体回滚。

### 6.2 结算

- 可计费结果从组织钱包预扣转为实际扣费。
- 成员额度从 `held_credits` 转为 `consumed_credits`。
- 最终费用小于预扣时，多余部分同时释放回组织钱包和成员额度。
- 幂等重放不得重复增加成员消耗。

### 6.3 失败和退款

- 不可计费、供应商失败或取消任务时，同时释放钱包预扣和成员额度预占。
- 后续发生账务退款时，是否恢复原周期额度需要在实施前确定；建议恢复到原消费周期并保留调整记录，而不是增加当前周期额度。
- 成员已离开组织不影响历史订单退款，退款仍返回原组织钱包。

## 7. 成员生命周期

### 7.1 加入组织

建议由组织管理员从无组织用户中添加成员。平台管理员只负责指定初始组织管理员，不操作普通成员。

加入组织后：

- 新消费使用组织钱包。
- 原个人钱包余额保持不变，不自动转入组织钱包。
- 原个人账本继续可审计。

### 7.2 离开或更换组织

- 有未结束计费任务时，建议先禁止离开，或等待任务结算后再完成成员变更。
- 离开后新消费恢复使用个人钱包。
- 历史消费仍归原组织。
- 更换组织应建模为先离开再加入，不直接覆盖组织 ID。

### 7.3 删除用户或组织

- 有账本、订单或成员历史的组织不得物理删除，只能停用。
- 删除用户前必须处理活跃成员关系；历史订单保留用户快照或可空外键。
- 删除组织管理员前必须先保证组织仍有其他管理员。

## 8. API 与授权

### 8.1 登录身份

登录校验响应可新增向后兼容字段：

```json
{
  "organization": {
    "id": "org-id",
    "name": "组织名称",
    "is_admin": true
  }
}
```

无组织用户返回 `organization: null`。不得把组织管理员映射成全局 `admin` 角色。

### 8.2 平台管理员 API

建议独立于用户管理接口：

- `GET /api/admin/organizations`
- `POST /api/admin/organizations`
- `PATCH /api/admin/organizations/{organization_id}`
- `PUT /api/admin/organizations/{organization_id}/admins`

这些接口只管理组织及组织管理员，不提供普通成员和成员额度操作。

### 8.3 组织管理员 API

- `GET /api/user/organization/members`
- `POST /api/user/organization/members`
- `DELETE /api/user/organization/members/{user_id}`
- `PATCH /api/user/organization/members/{user_id}/quota`
- `GET /api/user/organization/usage`

服务端从当前登录用户解析组织，客户端不得提交一个可自由切换的 `organization_id` 作为授权依据。即使请求中存在组织 ID，也必须与当前组织管理员身份交叉校验。

### 8.4 数据可见性

组织管理员可以查看本组织成员的：

- 登录 ID、姓名、成员状态和额度。
- 指定周期的积分消耗、原始 Token 数和调用次数。

默认不允许查看成员的对话正文、提示词、上传文件或任务产物。消费报表只提供计费和审计所需元数据。

## 9. 客户端设计

- 平台管理后台增加“组织管理”，用于编辑组织和设置组织管理员。
- 工作台侧边栏只在 `organization.is_admin == true` 时显示“成员 / Token 消耗”。
- 页面包含“成员”和“Token 消耗”两个页签。
- 成员页用于添加、移除成员以及设置额度。
- Token 消耗页复用现有统计页的筛选和表格交互，但使用组织范围专用接口。
- 菜单隐藏只负责体验，所有权限边界仍由服务端执行。

## 10. 充值、余额显示与提醒

实施前必须明确组织充值入口。建议：

- 普通组织成员不能直接给组织钱包充值。
- 组织管理员可以看到组织余额并执行组织充值，或由平台线下运营充值。
- 成员原个人余额可以显示为“个人余额（加入组织期间不使用）”，避免用户误解资产丢失。
- 组织低余额提醒只发送给组织管理员，不发送给全部成员。
- 多名组织管理员共享同一告警状态，但通知投递按管理员分别记录。

组织提醒需要独立于当前按 `user_id` 保存的个人余额提醒，不能把组织余额告警挂到某一位管理员个人钱包上。

## 11. 报表与审计

组织报表至少支持：

- 日、周、月或自定义周期。
- 按成员统计实际消耗积分、Token 数和调用次数。
- 组织总消耗与成员合计可对账。
- 预扣、实际结算、释放、退款和人工调整可追溯。
- 成员离开后仍可出现在历史周期中。

组织钱包本身只能给出组织总额，成员排行必须使用消费订单中的 `payer_user_id` 和组织快照计算。

## 12. 兼容与发布计划

建议分阶段实施，任何阶段都不批量迁移现有用户余额：

1. 新增组织、成员和额度周期表，所有现有用户保持无组织。
2. 登录接口返回可选组织身份，客户端暂不展示入口。
3. 引入统一计费主体解析器，以影子日志验证所有入口的解析结果，但仍使用个人钱包扣费。
4. 实现组织钱包与成员额度的原子预扣、结算、释放和退款。
5. 上线组织管理员 API 和平台组织管理 API。
6. 上线管理后台和工作台“成员 / Token 消耗”页面。
7. 仅对内部测试组织启用组织计费，对账稳定后按组织逐步开放。

需要支持按组织关闭功能的开关。关闭后不应破坏已创建订单的结算，只有新订单恢复到明确约定的策略。

## 13. 必须保持的系统不变量

- 一个用户同时最多属于一个启用组织。
- 无组织用户永远使用个人钱包。
- 组织成员的新消费永远使用消费开始时解析出的组织钱包。
- 组织钱包和成员额度不会因并发请求发生超扣。
- 预扣、结算、释放和退款均可幂等重放。
- 历史消费归属不会因成员关系变化而改变。
- 组织管理员不能访问其他组织数据。
- 组织管理员不会获得平台管理员权限。
- 平台管理员接口不提供普通成员和成员额度操作。
- 组织总消耗与成员消耗合计可以通过账本对账。

## 14. 验证范围

后续实施至少需要覆盖：

- 数据库迁移在 PostgreSQL、SQLite 上可重复执行。
- 现有无组织用户的登录、钱包、充值、扣费、提醒和报表回归。
- 多成员并发预扣不会超过组织余额或个人额度。
- 最终结算小于、等于和大于预估值时的处理。
- 供应商失败、取消、超时、重试、暂停后恢复和退款。
- 成员存在运行中任务时的退出和换组织行为。
- Open API 发布绑定用户的组织计费解析。
- AIGC、专家团、自动化和后台任务的付款主体一致性。
- 组织管理员跨组织访问、越权修改额度和伪造成员 ID。
- 组织管理员被撤销、组织停用和最后一名管理员变更。
- 组织积分报表、Token 报表和钱包账本对账。
- 旧客户端面对新增登录字段和新服务端版本仍可正常工作。

## 15. 实施前待确认的产品决策

以下问题不影响保存本设计，但必须在进入开发前确认：

1. 成员额度按自然月、充值周期还是自定义周期重置。
2. 未使用额度是否结转，以及额度调整从当前周期还是下一周期生效。
3. 是否允许不限额成员。
4. 组织管理员能否修改自己的额度；如果不能，由谁设置。
5. 一个组织是否允许多名组织管理员，建议允许且至少保留一名。
6. 组织管理员是从现有无组织用户中添加成员，还是可以直接创建新用户或发送邀请。
7. 普通成员充值进入个人钱包还是禁止充值；建议加入组织期间禁止误充个人钱包。
8. 组织停用后，运行中任务如何结算，新任务是否立即禁止。
9. 退款是否恢复原消费周期额度；建议恢复原周期并记录调整。
10. 组织管理员看到的是积分、原始 Token，还是两者都显示；建议两者分列展示。

这些决策确认后，应先更新本文档状态和结论，再开始数据库和计费链路实现。
