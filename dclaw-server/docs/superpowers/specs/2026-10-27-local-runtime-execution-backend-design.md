# DClaw 本地运行模式与统一 Local Runtime 设计

状态：`draft`

日期：`2026-10-27`

## 1. 背景

DClaw 当前以服务端托管执行为默认模式。桌面客户端已经可以连接 Windows 本地助手，`dclaw.super-agent-support` 插件也已经提供 `dclaw.local-execution` 合同、设备连接、任务生命周期和本地能力包机制，但现阶段主要用于超级专家的视频等本地制作任务，还不是面向普通项目的完整本地执行后端。

用户使用习惯正在转向“Agent + 本地项目目录 + 会话”的工作方式。DClaw 需要增加本地运行模式，同时保证既有托管模式、普通对话、普通 Agent、超级专家、OpenAPI 和计费链路不因本地组件缺失或故障而受到影响。

本设计采用“现有托管模式保持默认，新增可选本地执行后端”的演进方式。DClaw 桌面客户端仍是唯一业务界面和登录入口；本地组件是由客户端管理的后台 Runtime，不形成第二套产品。

## 2. 目标

1. 用户创建项目时可以选择“托管模式”或“本地模式”，默认仍为托管模式。
2. 本地模式能够在用户明确授权的项目目录中运行 Agent、文件、Shell、Git 和扩展能力。
3. Windows 和 macOS 使用同一公开协议、权限语义和产品流程。
4. 复用 DClaw 现有身份、会话、模型网关、MCP、技能、超级专家、计费和产物登记能力。
5. Local Runtime Core 保持业务无关；视频等大体积依赖由签名 Capability Package 按需安装。
6. Local Runtime 未安装、离线、升级失败或崩溃时，托管模式和其他现有功能继续正常运行。
7. 通过功能开关、白名单、独立测试环境和可回滚版本逐步上线。

## 3. 非目标

- 不替换或重写当前托管执行链路。
- 不要求已有用户迁移项目或安装 Local Runtime。
- 不为本地模式创建第二个有界面的桌面应用、账号体系或登录流程。
- 不允许 Capability Package 导入 DClaw Server、客户端或 Runtime 的私有模块。
- 不把 FFmpeg、Whisper、模型、字体等业务依赖打进最小 Runtime Core。
- 第一阶段不支持纯网页直接访问浏览器所在电脑的任意目录。
- 第一阶段不承诺离线使用全部 DClaw 云端能力。

## 4. 核心决策

### 4.1 两种执行模式

| 项目模式 | 执行位置 | 项目文件 | 默认状态 |
|---|---|---|---|
| 托管模式 | DClaw 服务端 | 服务端工作区 | 默认，保持现状 |
| 本地模式 | 用户设备上的 Local Runtime | 用户授权的本地项目目录 | 可选，按白名单开放 |

项目创建后必须持久保存执行模式。第一阶段不支持直接修改现有项目的模式；如需切换，应创建新项目并通过显式导入流程迁移文件，避免同一项目在两套文件系统之间产生不明确状态。

### 4.2 唯一客户端

DClaw 桌面客户端负责：

- 登录、项目和会话界面；
- 创建本地项目时选择目录；
- 展示 Runtime 安装、连接、版本和升级状态；
- 展示并收集操作审批；
- 启动、停止和升级后台 Runtime；
- 把已认证设备与当前 DClaw 用户绑定。

Local Runtime 不提供业务窗口和第二套登录。系统托盘或诊断窗口只能用于运行状态和故障排查，不承载业务流程。

### 4.3 Runtime 与能力包分层

```text
DClaw Desktop Client
  -> Local Runtime Core
       -> Project Sandbox / Permission Broker
       -> File / Shell / Git Executors
       -> Capability Package Manager
            -> Video Package
            -> Audio / Image Package
            -> Super Expert Packages
```

Local Runtime Core 只提供通用能力：

- 设备身份、配对、心跳和协议协商；
- 本地项目注册与目录授权；
- 沙箱、进程、资源和网络策略；
- 文件、Shell、Git 等通用执行器；
- 任务启动、继续、取消、恢复、日志和产物状态；
- 权限审批和审计事件；
- Capability Package 的验签、安装、升级、回滚和卸载；
- 缓存、磁盘配额和清理。

Capability Package 声明并携带业务依赖、准确版本、资源摘要和所需权限。视频制作依赖只有在用户首次使用对应能力时才安装。

### 4.4 复用业务流程但不导入 Core 私有实现

本地执行后端不逐项复制模型、MCP、技能、计费和超级专家逻辑，也不直接导入 DClaw Core 私有代码。DClaw 应提供稳定、版本化的 Host API：

```text
Conversation / Agent Orchestrator
  -> Execution Backend Router
       -> Managed Backend (existing)
       -> Local Backend Adapter
            -> Local Runtime Protocol

Local Runtime / Capability Package
  -> DClaw Host API
       -> Model Gateway + Billing
       -> MCP Broker
       -> Agent / Super Expert Metadata
       -> Skills and Grants
       -> Conversation Events
       -> Artifact Registry
```

Host API 必须从已认证上下文派生用户、租户、项目、Agent、会话、设备和授权信息。Runtime 或能力包不能通过请求参数覆盖这些身份字段。

## 5. 组件边界

### 5.1 DClaw Core

DClaw Core 只拥有业务无关的公共 SPI：

- `ExecutionBackend` 注册、选择和生命周期；
- 已认证的项目、会话、Agent、用户和租户上下文；
- 通用模型、MCP、技能、计费和事件基础设施；
- 插件注册与功能开关；
- 通用审计和追踪。

Core 不得硬编码本地能力包、Runner 版本、视频业务字段或具体超级专家名称。

### 5.2 `dclaw.super-agent-support` 与本地执行插件

现有 `dclaw.local-execution` 合同、设备通道、任务状态和能力包机制作为演进基础。实现时需评估两种归属：

1. 将可供普通 Agent 和超级专家共同使用的部分提升为通用 `local-runtime` 平台插件；
2. 保留超级专家适配在 `dclaw.super-agent-support`，通过公开 SPI 依赖通用 `local-runtime` 插件。

不能让普通本地项目反向依赖 Super Agent 专属实现。最终归属必须在编码前通过依赖图和“插件未加载”回归测试确定。

### 5.3 Local Backend Adapter

服务端或客户端适配层负责把统一的 Agent 工具调用转换为本地任务协议，包括：

- 选择绑定到项目的在线设备；
- 校验 Runtime 和协议兼容性；
- 投递带幂等键和 `trace_id` 的任务；
- 转发审批、检查点、进度、结果和错误；
- 将本地产物登记到当前会话；
- 保持 DClaw 统一的计费和终态语义。

### 5.4 Local Runtime Core

Runtime 是 Windows/macOS 上的后台组件。不同平台可以采用不同实现，但必须通过相同合同测试。Runtime 不能理解开放式客户意图、选择业务供应商或判断业务结果。

### 5.5 Capability Package

能力包只实现已签名合同内的确定性技术能力。每个包至少声明：

- package、capability 和合同版本；
- 支持的操作系统与 CPU 架构；
- 最低 Runtime 版本；
- 文件、进程、网络、设备和资源权限；
- artifact URL、允许域、大小和 SHA-256；
- SBOM、许可证与签名者；
- 安装、健康检查、回滚和卸载入口。

## 6. 用户体验

### 6.1 创建项目

创建项目入口提供两种模式：

- **托管模式**：默认选中，界面和行为保持现状。
- **本地模式**：选择本机项目目录，并检查 Runtime 状态。

只有用户选择本地模式后，客户端才执行 Runtime 检测。不能在登录、启动客户端或进入普通托管会话时强制提示安装。

### 6.2 首次本地使用

```text
选择本地模式
  -> 检查平台与 Runtime 状态
  -> 未安装：说明大小、权限和安装来源
  -> 安装最小 Runtime Core
  -> 选择并授权项目目录
  -> 创建项目与设备绑定
  -> 进入会话
```

首次本地项目不安装视频等可选包。执行某项能力时，客户端展示该能力包的发布者、大小、权限和磁盘占用，再按需安装。

### 6.3 本地会话界面

本地模式增加：

- 项目目录与更换/重新授权入口；
- Runtime 在线状态、版本和诊断入口；
- 当前执行权限级别；
- 当前设备和项目绑定状态；
- 能力包安装或升级进度。

托管模式不显示本机目录选择和本地 Runtime 状态。已有通用权限控件可以保留，但必须根据执行后端显示准确语义。

### 6.4 Web 客户端

Web 页面不能直接获得任意本地目录能力。第一阶段规则：

- Web 创建项目只提供托管模式；或
- Web 仅能选择已经由桌面客户端创建、授权并在线的本地项目，所有敏感审批仍在对应桌面设备完成。

不使用浏览器文件选择器模拟长期项目目录授权。

## 7. 目录与权限模型

目录边界和操作审批是两个独立维度。

### 7.1 目录授权

- 每个本地项目绑定一个规范化后的项目根目录和一个设备。
- Runtime 保存操作系统提供的持久授权句柄或等价安全引用；服务端不保存可直接访问的本机绝对路径凭证。
- 所有相对路径解析后必须仍位于项目根目录内。
- 符号链接、junction、大小写折叠和路径穿越必须按平台分别测试。
- 项目外访问需要单独、可撤销的显式授权，不能由“完全访问”自动获得。

### 7.2 操作审批

首版至少提供以下策略，最终文案由客户端多语言资源统一维护：

| 策略 | 行为 |
|---|---|
| 操作前询问 | 写文件、执行命令、网络访问等敏感操作按策略请求批准 |
| 项目内自动 | 已声明能力可在项目根目录内执行，越界和高风险操作仍需批准 |
| 受控完全访问 | 减少操作级确认，但仍受目录授权、能力清单、系统权限和禁止规则约束 |

“完全访问”不是操作系统管理员权限，也不允许绕过项目边界、签名能力、网络允许域和平台禁止规则。

### 7.3 默认拒绝项

至少包括：

- 未经授权读取项目根目录外的用户文件；
- 静默提权或修改系统安全配置；
- 读取浏览器、SSH、云服务等凭据目录；
- 将本地文件上传到未声明域名；
- 能力包自更新、修改 Runtime Core 或安装常驻服务；
- 从模型文本直接拼接并执行未经过结构化校验的特权命令。

## 8. 协议演进

现有 `dclaw.local-execution` 工具继续作为能力包任务基础：

- `local_environment_status`
- `local_capabilities_list`
- `local_runtime_prepare`
- `local_task_start`
- `local_task_continue`
- `local_task_status`
- `local_task_cancel`
- `local_task_result`
- `local_file_select`
- `local_file_upload`

通用本地项目需要在兼容演进中补充或明确：

- 项目注册、目录授权和撤销；
- 项目与设备绑定；
- 通用 File/Shell/Git 能力描述符；
- 审批请求、批准、拒绝和过期；
- 流式 stdout/stderr 与截断规则；
- Runtime 自身安装、版本协商、升级和回滚状态；
- 客户端断线、服务端断线和进程重启后的任务恢复；
- 本地产物只登记元数据或由用户明确选择上传的语义。

协议必须使用版本化 Schema 和兼容夹具。新增字段优先向后兼容；改变权限或必填字段时发布新合同版本。

## 9. 安装、升级与卸载

### 9.1 最小安装

最小 Runtime Core 应尽量只包含连接、权限、沙箱、任务和包管理能力。安装包按以下维度独立发布：

- Windows x64 / arm64（按实际支持范围）；
- macOS arm64 / x64（按实际支持范围）；
- Runtime 版本；
- 协议版本。

### 9.2 可信更新

- 客户端只从 DClaw 声明的 HTTPS 来源下载；
- 安装前验证代码签名、发布签名、大小和 SHA-256；
- 使用临时目录准备并原子切换；
- 健康检查失败自动恢复上一可运行版本；
- 不因 Runtime 更新失败阻止客户端登录或托管模式使用。

### 9.3 能力包按需安装

Runtime 根据签名描述符安装能力包及其资源。不同包可以共享内容寻址缓存，但不能共享可变工作目录或权限。卸载项目不应自动删除仍被其他项目引用的共享资源。

## 10. 数据与状态

服务端建议保存：

- 项目执行模式；
- 用户、项目和设备的不可变绑定 ID；
- Runtime/协议/能力目录版本及在线状态；
- 权限策略和授权摘要，不保存本机访问凭证；
- 任务、审批、检查点、结果元数据和审计记录；
- 能力包安装状态与版本；
- `trace_id`、计费关联和产物登记。

设备端保存：

- 设备私钥与配对凭证；
- 操作系统目录授权句柄；
- 本地项目路径；
- Runtime、能力包和资源缓存；
- 可恢复任务、检查点和有限诊断日志。

设备端敏感数据必须使用系统安全存储，并提供解绑、撤销和本机清理操作。

## 11. 功能开关与兼容

建议最少设置：

- 全局本地模式开关；
- 租户/用户白名单；
- 平台与架构开关；
- File、Shell、Git 等能力开关；
- Capability Package 发布通道；
- Web 连接桌面设备开关。

所有本地模式入口必须由能力发现决定，不能仅靠前端隐藏。关闭开关后已有托管项目不受影响；已有本地项目显示明确的暂不可用状态，不得静默切换到服务端执行。

## 12. 故障与回滚

| 故障 | 预期行为 |
|---|---|
| Runtime 未安装或离线 | 仅本地项目不可执行，提示安装或重连 |
| Runtime 版本不兼容 | 阻止本地任务并提供升级，不影响托管任务 |
| 能力包安装失败 | 回滚该能力包，其他能力与 Runtime 保持可用 |
| 本地任务进程崩溃 | 保存终态或恢复信息，不重复产生未声明副作用 |
| 客户端关闭 | 可恢复任务按策略继续或暂停，重连后查询状态 |
| 服务端断线 | Runtime 不接收新云端命令；在安全策略内保存当前任务状态 |
| 权限被撤销 | 立即阻止新访问，当前任务进入明确失败或等待状态 |
| 本地功能全局关闭 | 本地项目停止新任务；托管链路完全不变 |

不得在本地执行失败后静默改由服务端执行，因为文件位置、权限、费用和副作用都不同。

## 13. 测试环境设计

亚马逊测试服务器作为独立 DClaw 控制面环境，必须与生产隔离：

- 独立域名或测试地址；
- 独立数据库、Redis、对象存储前缀或桶；
- 独立密钥、OAuth 回调、外部应用和 API Key；
- 独立插件状态目录、日志和备份；
- 测试账号及功能白名单；
- 禁止连接生产数据库、生产对象存储写入权限和生产回调地址。

测试服务器不能替代真实客户端测试。完整拓扑为：

```text
AWS Test DClaw
  <-> Windows DClaw Client + Windows Local Runtime
  <-> macOS DClaw Client + macOS Local Runtime
```

环境评估先执行只读检查：操作系统与架构、Docker/Compose 版本、CPU/内存/磁盘、端口、域名/TLS、反向代理、时钟、现有容器和网络、数据服务、备份位置及日志策略。未经单独批准，不构建镜像、不部署、不重启、不修改防火墙和数据。

## 14. 分阶段实施

### Phase 0：设计与基线

- 确认组件归属和依赖图；
- 记录现有托管模式、超级专家和本地助手回归基线；
- 定义 Execution Backend SPI、Host API 和威胁模型；
- 盘点 Windows Helper 可复用与需拆分的代码；
- 只读评估 AWS 测试环境。

退出条件：设计评审完成，公开合同和安全边界没有未决阻塞项。

### Phase 1：最小本地项目闭环

- 客户端创建本地项目、选择目录和展示状态；
- Windows Runtime Core；
- 项目绑定、目录授权和最小文件能力；
- 执行后端路由、任务状态、审计和功能开关；
- 托管模式零影响回归。

退出条件：白名单账号可在测试环境完成本地项目文件任务，关闭功能后现有功能不变。

### Phase 2：开发工具与 Host API

- Shell、Git、审批和沙箱；
- MCP Broker、模型网关、技能和计费复用；
- 断线恢复、取消、产物登记和诊断；
- Windows 内部灰度。

退出条件：代表性编码任务端到端完成，权限、计费和恢复测试通过。

### Phase 3：能力包统一

- 将现有视频依赖从助手核心边界中明确拆为能力包；
- 统一包签名、按需安装、共享缓存、升级、回滚和卸载；
- 超级专家通过 Host API 和统一 Local Runtime 运行本地能力。

退出条件：视频既有用例能力不回退，普通本地项目无需下载视频依赖。

### Phase 4：macOS 与扩大灰度

- macOS Runtime；
- 同一合同测试跨平台通过；
- 内部账号、友好客户、租户级灰度；
- 性能、安全和运维验收。

退出条件：Windows/macOS 兼容矩阵、升级与回滚演练通过，再决定公开范围。

## 15. 验收与测试

### 15.1 托管模式零侵入

- Runtime 未安装时可正常登录、创建托管项目和对话；
- 本地插件禁用、加载失败和升级失败时普通 Agent 正常；
- 托管项目的工作区、工具、MCP、技能、SSE、计费和错误语义不变；
- 客户端启动不主动弹出本地安装要求。

### 15.2 本地功能

- 新建、打开、重命名和删除本地项目的明确语义；
- File/Shell/Git 在授权目录内正确执行；
- 路径穿越、符号链接和越界访问被拒绝；
- 审批批准、拒绝、过期和撤销均有确定终态；
- 任务取消、客户端重启、Runtime 重启和网络中断可恢复；
- 能力包按需安装，签名或摘要错误时失败关闭；
- 产物不会未经授权上传；
- Windows/macOS 对相同合同返回一致错误类别。

### 15.3 安全与运维

- 设备解绑后旧凭证不能继续连接；
- 跨用户、跨租户、跨项目和跨设备调用被拒绝；
- 日志不包含令牌、私钥和本机敏感文件正文；
- Runtime 与能力包升级可独立回滚；
- AWS 测试环境可备份、恢复并验证数据隔离；
- 所有层可通过同一 `trace_id` 定位任务。

## 16. 主要风险

| 风险 | 等级 | 控制措施 |
|---|---|---|
| 本地命令与文件权限扩大攻击面 | 高 | 项目根目录边界、结构化工具、审批、沙箱、签名与审计 |
| 双执行后端产生行为差异 | 高 | 统一 Host API、合同测试、禁止静默回退、明确兼容矩阵 |
| macOS/Windows 系统能力不同 | 中高 | 协议先行、平台适配层、同一黑盒合同套件 |
| Runtime/能力包供应链 | 高 | 代码签名、发布签名、SHA-256、SBOM、允许域、原子升级回滚 |
| 现有托管模式回归 | 高 | 新插件、功能开关、依赖反转、插件缺失测试和全量回归 |
| 本地任务与云端会话状态不一致 | 中高 | 幂等键、检查点、持久任务、确定终态和 `trace_id` |
| 安装体积与升级体验 | 中 | 最小 Core、能力包按需下载、内容寻址缓存和磁盘管理 |
| 测试环境误连生产 | 高 | 独立密钥和数据服务、出站/入站检查、部署前环境门禁 |

## 17. 编码前决策门禁

以下事项确认后才能开始影响公开合同的实现：

1. 通用 Local Runtime 插件与 `dclaw.super-agent-support` 的最终所有权边界。
2. Execution Backend SPI 和 Host API 的首版接口、身份派生和计费责任。
3. Windows/macOS 沙箱技术选型与第一阶段可承诺的隔离强度。
4. 本地项目目录授权在 Tauri、Windows 和 macOS 的持久化方案。
5. Shell 首版审批粒度及明确禁止规则。
6. Runtime 安装、签名、自动升级和回滚的发布基础设施。
7. Web 端是否只展示托管模式，还是允许连接已授权桌面设备。
8. AWS 测试环境的域名、数据隔离和客户端连接方案。

## 18. AWS 环境评估所需信息

- SSH 主机或 IP、端口和用户名；
- 本机已有 SSH 私钥路径及是否可以使用 `sudo`；
- 测试域名和 DNS 管理方式（如已有）；
- 当前 Docker/Compose、反向代理和 TLS 的管理方式；
- 是否已有专用 PostgreSQL、Redis 和对象存储；
- 允许使用的端口范围与安全组变更负责人；
- 测试数据保留、备份和费用限制；
- 明确允许检查、安装、部署和重启的操作边界。

环境信息中的密码、Token 和私钥内容不得写入本文、聊天记录或仓库。
