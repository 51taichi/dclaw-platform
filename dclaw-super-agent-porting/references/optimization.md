# 优化迭代模式

本文件只用于 `optimization`。先读取主 `SKILL.md`，再执行本文件；主文件中的依赖、职责边界、公共 Component、密封、上传、授权和激活门禁继续有效。

## 执行顺序

```text
锁定当前正式版本、优化目标和回滚版本
  -> 判断受影响节点与旧证据有效性
  -> 按需复核 Node 1–4；失效证据补齐
  -> Node 5 实现批准的优化
  -> Node 6 问题复现、目标验证与回归验收
  -> Node 7 新版本密封与独立验签
  -> Node 8 上传、授权与激活
  -> 移交项目方客户验收
```

优化必须形成新版本。不得覆盖、重签或删除当前正式版本，也不得在未记录差异和验收依据的情况下直接修改发布物。

若当前专家使用动态 AIGC 工作流创建工具，取得实际激活 Release 的代码和脱敏运行证据后，按[创建副作用门禁](aigc-effect-route.md)逐项核对原创建入口、模型仅读目录、创建后正文缺失、未知终态、重复请求和旧状态恢复。当前生产运行快照可用作只读行为基线，但不能代替原始工程、构建输入或发布权限；新版本须在本 Agent 自己的项目里实现和测试。共享 Skill 的更新不自动修复旧已签名包。

## 启动门禁：锁定迭代基线

若开发方只提供原专家的运行快照，先将快照版本与目标实例当前激活 Release 对照，确认原 `agent_id` 的所有者、signer 和发布权限，并盘点缺失的源工程、测试及构建输入。可以在独立工作区重建和验证受影响部分；快照文件存在或复用原 ID 都不代表已取得原专家的更新权，也不能跳过下述基线与新版本门禁。

没有可编辑源工程时先查开发方已有项目、版本库或其提供的代码包，再核目标实例当次正式标准是否提供所有者可用的源码导出。已核验的标准 2.61 明确管理后台不提供源文件查看、克隆、导出或下载，不能把当前激活 Release 的列表回读当作源码下载入口；若将来正式合同新增导出，按当次权限与回执使用。只有运行快照时按上段重建并标明未恢复的构建输入和业务行为，不能声称已取得原项目源码。

进入受影响节点前，先读取当前 Agent 的项目、正式发布证据和真实运行材料，形成以下基线：

| 项目 | 结论 | 证据或待确认原因 |
|---|---|---|
| `agent_id` |  |  |
| 当前正式版本 |  |  |
| 当前激活密封包/manifest |  |  |
| 当前私有能力制品 |  |  |
| 当前业务行为 |  |  |
| 问题或优化目标 |  |  |
| 预期结果 |  |  |
| 允许修改范围 |  |  |
| 必须保持不变的范围 |  |  |
| 业务验收案例 |  |  |
| 回滚版本 |  |  |

先从用户指令、问题证据、日志、`trace_id`、当前代码和真实产物提取已知内容，不要求用户重复回答。只有会改变优化范围、依赖、兼容策略或验收结论的缺失信息才列为待确认。

当前正式版本、优化目标、保持不变范围、验收案例和回滚版本全部明确后，先列出受影响节点及旧证据是否仍有效，再进入首个需复核的节点。未受影响节点保留证据路径与有效性理由，不重做整轮材料。

## 问题归属

在修改 Agent 前先判断问题所属环节：

| 问题类型 | 处理方式 |
|---|---|
| Agent 业务逻辑、卡片、状态机或私有能力问题 | 进入本优化流程 |
| 已发布平台公共合同的实现 Bug | 交由 DClaw 平台维护方修复；Agent 不增加私有绕过逻辑 |
| 缺少可供所有 Super Agent 使用的平台通用能力 | 提交平台能力申请，取得确认前停止受影响链路 |
| 第三方 API、凭证、费用或供应商行为问题 | 由 Agent 业务实现按其合同处理 |
| 客户账号、人工验证或设备环境问题 | 明确用户操作和恢复入口，不伪装为代码成功 |

一个问题涉及多个环节时分别记录，不把平台、Agent、第三方或客户错误合并为模糊的“生成失败”。

## Node 1：依赖影响复核

先将当前签名 Release 的依赖清单、业务调用覆盖记录与本轮变更对照。依赖调用、目标平台、公共 Component 或调用合同没有变化，且旧证据能对应当前签名版并仍适用时，记录引用与影响判断，Node 1 不重做。涉及变化时检查受影响调用及上下游分支，用目标实例最新完整 Registry 和正式 DevKit/Runner 合同核对当前发布范围内的公共依赖；旧覆盖记录缺失、无法对应签名版或发现漏检时，按主 Skill 完整盘点。不能仅凭依赖文件或版本号声称无影响。

固定五列表继续使用主 Skill 格式，在`备注建议`中标明变化类型：

- `保持`：优化前后都需要，版本和调用合同不变；
- `新增`：优化后新引入；
- `替换`：用另一个依赖或注册版本替代；
- `升级/降级适配`：按 Registry 注册版本调整；
- `移除`：优化后所有流程都不再使用，必须有完整调用覆盖证据。

进入 Node 1 后，优化版仍需使用的所有公共依赖必须为 `available`；未变化项可引用本次核对后仍有效的证据。新增、替换或版本适配项为 `reserved`、`absent` 或 `unverified` 时，受影响链路保持 Node 1 blocked，不得将其作为已适配能力发布；不依赖该项的批准范围及离线测试可继续。若缩减本轮优化范围，须先取得逐项确认并重核依赖和回归门禁。

## Node 2：当前流程与优化流程对照

业务流程或 DClaw 承载发生变化，或当前版图表缺失、无法对应签名版时进入 Node 2。第一张图必须来自当前正式版本的真实代码和运行行为；第二张图只展示已批准的优化结果。两张图使用相同业务步骤编号，并同时输出差异表：

| 步骤 | 当前行为 | 优化后行为 | 修改原因 | 验收标准 |
|---|---|---|---|---|

没有进入差异表的步骤、字段、判断、人工操作和最终产物默认保持不变。优化后删除或合并步骤时也必须在差异表中记录去向和验收方式。

存在无法解释的新增业务、范围外变化或当前行为未被真实证据覆盖时，Node 2 不通过。

## Node 3：职责与能力影响

职责或能力归属变化时进入 Node 3；未变化且证据仍有效时引用旧映射。进入本节点时使用主 Skill 的责任映射，并为受影响能力标记变化状态：

| 业务步骤/能力 | 当前责任位置 | 优化后责任位置 | 状态 | 输入输出变化 | 失败归属 |
|---|---|---|---|---|---|

`状态`只能为`保持`、`修改`、`新增`或`移除`。责任位置发生变化时，必须重新核对 Agent、业务服务、本地助手和平台插件边界。不得通过把 Agent 私有逻辑放入 DClaw 核心或公共插件完成优化。

## Node 4：合同与兼容设计

合同或兼容性变化时进入 Node 4；旧合同证据缺失或已失效时也须补核。对所有变化项记录修改前后合同：

- 卡片字段、顺序、默认值和校验；
- 答案驱动业务写入时，核对密封运行时可核验的答案来源，以及卡片身份、版本、提交事件与当前授权主体的关联合同；回执摘要和模型候选不能代替答案；
- 正式材料已有可信作用域的 Host 读卡能力时，先核对签名声明、安装授权与关闭 Schema，再接通并验证原始结果与提交回执的关联；只有模型工具的旧合同按其正式结果边界核验，尚未调用现有能力不能算平台能力缺口；
- 工作流状态、分支、重试和恢复；
- 第三方 API 请求、响应、错误、费用和超时；
- 本地任务输入、输出、检查点和产物；
- 能力清单、公共 Component 和 Runner 最低版本；
- 客户提示、结构化错误和 `trace_id`；
- 客户可见交付内容与呈现格式，以及内部候选、可信状态和诊断信息的可见性边界；涉及 `agent.execute` 时按正式合同确定公开流设置与最终提交路径；
- 正在执行的旧任务和已保存状态如何处理；目标实例若支持 `workspace.state.continuity/1`，核对新旧签名包的状态声明、签名者、格式与 Schema 版本、实际文件名、来源修订完整性，以及新版本首次业务回合前的续接条件。新包声明不能替代缺声明旧包的兼容登记；
- 新版本失败后回滚到上一版本时的数据与状态兼容。

未变化的合同保持原样。合同变化必须使用目标实例正式 DevKit 已公开的能力和 Schema；不能读取平台源码或复制其他 Agent 的字段来补合同。

## Node 5：实现优化

只实现本轮批准的内容；业务流程或合同发生变化时，以受影响的 Node 2 差异表和 Node 4 合同为准：

若 Node 4 的平台合同仍缺失，可继续开发已批准范围内且不依赖该合同的纯业务逻辑与离线测试；记录为草稿，受影响的 Node 4/5 放行结论不因此变为已通过。

- 不顺便重构或修改范围外流程；
- 不新增未确认的业务、字段、供应商或本地链路；
- 不用 Agent 私有代码绕过平台公共问题；
- 不覆盖当前正式版本或复用其他 Agent 的发布物；
- 新发现依赖时回退 Node 1；
- 业务范围变化时回退 Node 2；
- 职责或平台边界变化时回退 Node 3；
- 合同不足时回退 Node 4。

## Node 6：问题复现、目标验证与回归验收

优化必须保留三组相互独立的证据：

| 证据组 | 目的 | 必须证明 |
|---|---|---|
| 问题复现 | 建立优化前事实 | 当前正式版本确实存在目标问题或限制 |
| 目标验证 | 验证本次变化 | 新版本达到本轮批准的验收标准；流程变化时对照差异表 |
| 回归验证 | 保护范围外行为 | 未批准修改的流程、卡片、能力和产物保持正常 |

按本轮影响范围测试适用的卡片、状态机、第三方 API、本地助手合同、失败恢复、旧状态兼容和真实业务案例；未受影响且证据仍有效的路径可引用旧结果，范围外回归按变更风险选取代表性路径。工具或接口返回成功不能代替最终业务结果验收。
答案驱动写入的卡片须测试提交回执存在但可信答案不可得、事件与本次回合无法关联、正式合同要求的可信答案读取未发生或失败，以及模型重试绕开必要工具的路径；这些路径须失败关闭，不得写入基于猜测答案的状态或产物。
对跨 Release 续接，先区分本地旧状态读取测试、平台维护回执和原任务真实续接。平台回执须能证明目标状态已提交或首轮自动续接已完成，并核对版本、引用、摘要和实际绑定文件；`publish list` 只能证明激活版，不证明作品状态已转入新 installation。没有原任务真实回合时，`e2e-verified` 仍为 `false`。
若本轮改变客户可见输出或修复内部内容外露，目标验证须检查受控 Host 下的最终回复、公开流参数及长内容排版；发布后的真实客户端显示和刷新回读另行验收。旧截图不能单独证明内部内容来自 Agent 提交还是平台展示，须按同一 invocation 核对，缺记录时保持未归因。

若优化针对反复出现的同类故障，三组证据还须说明共同失败机制与受影响范围，覆盖该机制的正常、失败和恢复路径；在可控环境对适用的失败分支做故障注入，并核对旧版对照、新版回归与范围外行为。无法注入时记录原因与替代证据。发布后按[试跑问题处理规则](runtime-feedback.md)核对监测、回滚条件和适用的真实任务复测；本地或官方测试不能替代生产结果。

如果无法复现旧问题，不能根据猜测修改；先补充运行证据或重新确认优化目标。

## Node 7：新版本密封与独立验签

按照主 Skill 和唯一标准执行，并额外满足：

- 保持同一个 `agent_id`；
- 使用新的版本号和独立发布证据；
- 重新计算摘要和签名；
- Super Agent 密封包与私有本地能力制品分别构建；
- 在干净目录独立验签；
- 若新版本有持久工作状态且目标合同要求声明，确认 `agent/state-contract.json` 符合当次官方 Schema、进入签名包，并与当前代码实际读写格式及文件名一致；
- 当前正式版本完整保留为回滚目标。

## Node 8：上传、授权与激活

继续使用同一账号名下的 `agent_id`，以递增语义版本重新执行当前正式 DevKit 的 `digest → validate → test → build → verify`；如 Pack 或 DevKit 已升级，先按官方 `upgrade` 合同处理项目元数据和兼容性。普通账号 `super_expert_public` 使用官方 `publish upload` 更新，核对新版本回执的 `state=active`、`visibility=public`、摘要和 `release_id`，再用 `publish list` 核对新的 `active_release_id`。整体授权依据当前正式原子发布合同推定，不编造独立 grant/installation ID。其他包类型按其正式合同分别取得授权、安装、激活证据；上传成功但未激活时不得称为上线。

不得删除或覆盖回滚版本。缺少目标环境、当前发布方式所需的账号权限、可信 signer 或本次公开发布授权时保持 Node 8 blocked，并准确报告阻断环节。
若旧已签 Release 缺状态声明而新版将首次加入声明，先按目标正式合同核对是否需要平台维护方以两个发布摘要及一致的已签状态代码登记 legacy 兼容关系。该登记只能由平台维护方预检后执行，不能改写旧包或由开发方伪造；新版状态结构不兼容时须先有显式迁移方案。自助上传若同时激活，而登记需要新版发布记录，必须在上传前取得平台确认的安全顺序、失败关闭与回滚办法及可核对的登记/续接回执；顺序未明确时 Node 8 保持 blocked，不以试传或新业务回合探路。此门禁仅适用于确有旧任务持久状态且依赖跨 Release 续接的更新。
目标正式合同若支持预检失败后保留未激活 Release，上传命令非零退出时仍须核对是否已生成 Release、安装授权和可重试的准确 ID。只读列表中旧版保持 active 不足以判定上传事务未发生；先定位脱敏错误类别和平台状态，再按正式合同选择修复后重试激活或另行处理，不直接重复上传。
已确认版本被未激活 Release 占用时，核对其不可变签名摘要。若失败源于该包的声明或代码，保留旧失败记录，用新语义版本重新密封更正包；只有原包正确且激活阻断已修复，才按正式合同对原 Release 重试激活。平台预检实现缺陷由平台维护方修复和回归，不靠 Agent 放宽真实状态冲突校验。

## Node 8 后移交

Node 8 完成后，本 Skill 的优化发布阶段结束。当前 Agent 开发者必须交付新版本的上传回执、列表回读、三组测试证据、已知限制和有效回滚版本，并如实记录 `e2e-verified`。按[下一步决策与续接](next-step.md)跟踪受影响能力的真实客户端验收；未验证或调用失败时保持 `false`，不得根据发布或客户端可见状态更新它。

项目方验收发现问题时，保持已有发布证据不变；根据问题归属使用新版本回退 Node 1、Node 2、Node 3、Node 4 或 Node 6。只有项目方提供明确验收确认与证据后，才能更新 `e2e-verified`。

## 完成条件

只有同时具备新版本激活回执、三组测试证据、有效回滚版本和“待客户验收”移交记录，才能宣称开发侧优化迭代完成。不得把该结论表述为“已通过真实客户验收”。后续新的优化目标必须开启下一版本并重新进入本流程。
