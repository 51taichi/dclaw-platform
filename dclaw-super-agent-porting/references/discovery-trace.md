# 需求澄清与节点追踪

本规则适用于 `new-development` 和 `optimization`。只澄清当前 Agent 的范围、流程、依赖和验收；业务方法由该 Agent 项目决定。本文件随 Skill 分发，不依赖其他访谈 Skill。

## 先读材料，再逐题确认

1. 在当前 Agent 项目中读取用户要求、业务材料、来源项目或当前正式版本、已有测试与发布记录。使用另一项目材料开发新专家时先保护原件并建立副本；访谈记录写在副本或目标项目中，原件不动。优化先核对当前正式版本与本轮批准范围。
2. 在项目内建立本轮记录文件，写明模式、Skill 版本、事实来源、已知决定和待确认项。若已有记录则续写同一份，避免产生互相冲突的基线。文件路径由项目约定决定，不使用 Skill 仓库保存项目资料。
3. 只问材料无法回答、且会改变本轮范围、业务步骤、依赖分类或验收结论的问题。一次问一个问题，给出基于现有证据的建议答案，供项目方确认或纠正；建议不能当作确认。
4. 每收到一项回答，先写入记录文件，再继续下一题。保留关键原话、事实来源、决定、影响的步骤和待办负责人；后续回答推翻旧决定时，更新同一记录并标明变更。不能回答的问题标为待确认，注明应由谁或哪份正式材料解决，继续处理不依赖它的工作。
5. 问到足以描述本轮流程、判断依赖并定义验收即可收束。核对记录中的矛盾和遗漏，确认或标出剩余待确认项；不要为完成固定题数而反复询问，也不要因与本轮无关的问题阻断工作。受待确认项影响的节点按主 Skill 门禁保留未放行状态。

记录至少能查到“问题或证据 -> 项目方回答/决定 -> 受影响步骤 -> 当前状态”。凭据、私钥和客户敏感资料只记录安全引用，不写入访谈记录或共享仓库。

## 一套稳定步骤编号

- 在 Node 0（优化为迭代启动基线）按真实执行顺序列出本轮业务链路。已有项目沿用其稳定编号，例如 `W01`；全新项目可用 `STEP01`、`STEP02`。业务步骤编号不得与镜头、素材、任务等实体编号混用；旧项目已有重名时，在图和测试记录中明确标注编号所属类型，不重排历史编号。每步写输入、处理、分支或人工决定、输出、失败与重试、完成判据和事实状态；不适用的字段可标明不适用。分支与返工要能回指明确步骤，不为套用示例重编历史记录。
- `new-development` 以确认的本轮目标流程编号；有来源材料时区分已验证、材料描述、未实现与未知，来源不完整仍可建副本和记录。已有测试先按来源修订、输入预期与结果映射到适用步骤，不要求旧签名包或固定数量的用例；未覆盖部分才补最小必要验证。`optimization` 保留当前正式流程的编号，新增步骤取新编号，删除或合并步骤保留旧编号及去向，不能重排编号掩盖变化。
- Node 2 的两张图沿用这些编号。第一张呈现对应模式的业务基准；第二张呈现 DClaw 承载或批准的优化后流程，并在每个步骤标明实际责任位置、能力或合同及输入输出差异。一个技术步骤承载多个业务步骤时列出全部编号；新增技术操作不能悄悄变成新业务决定。
- 建立按编号的对照表，至少记录 `步骤 | 事实来源/决定 | 业务基准 | DClaw 承载或优化变化 | 差异/待确认 | 验收判据`。流程图与表不一致时先修正，不能以图形完整代替事实核查。

## 逐节点测试与反馈

- Node 6 按本轮适用的每个步骤及关键分支建立测试记录：`步骤 | 场景/输入 | 预期结果 | 实际结果 | 证据位置 | 状态 | 问题归属`。覆盖正常、失败、重试、人工决定和最终交付中实际适用的路径；多个步骤共用一次端到端测试时仍注明各步骤的观察证据。
- Agent 若根据用户自由文本判断目标步骤，使用实际任务措辞测试路由；同一句话提及其他步骤、明确否定或禁止修改其他步骤时，核对选中的目标、调用次数和未选中步骤的状态副作用。不能只用单一关键词命中证明分流正确。
- 一次输入若要求依次执行多个会改变状态的动作，按该 Agent 已确认的业务合同测试动作顺序、每步使用的上游版本或引用及允许的提交边界；使后续一步失败，核对此前结果应保留或撤销的状态和客户可见内容，不把部分完成报告为整项成功。
- `new-development` 对照 Node 0 预期；声明沿用来源行为时，对可执行的来源与目标记录相同输入的对照，无法验证来源时标“等价待证”，有效离线测试优先作为本轮行为基线证据。`optimization` 分开记录旧问题复现、目标验证和范围外回归。离线测试、平台合同测试、上传激活和真实客户端使用分别记证据，不能互相替代。
- 收到运行问题时先确定实际激活版本、最早失败的步骤编号和对应证据，再按 `runtime-feedback.md` 分流。修复后回到受影响节点，更新两张图、对照表和相关测试；不受影响的已核验证据可以保留。未定位时记录“未归因”，不能猜测平台或业务根因。
