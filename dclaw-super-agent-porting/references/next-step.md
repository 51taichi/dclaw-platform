# 下一步决策与续接

本规则在首次接入、换对话续建、收到测试结果或平台回执、用户问“然后呢”时使用。它只决定**当前 Agent 项目**下一步由谁做什么；业务步骤仍由该项目定义。不要把某个案例的提示词、节点编号或客户端操作写成所有专家的固定流程。

## Codex 的引导循环

首次读完 Skill 后，给开发方一屏内的通用链路总览，即使尚未提供专家项目也要展示：`核对材料 → 新专家开发（可用现有材料）/未发布续建/已发布优化 → 适用 Node 0–6 的范围、适配和测试 → Node 7–8 的签名、上传与回读 → 真实试跑、排错与专家更新`；另用一行说明并行反馈链：`卡点留证并脱敏交本工作区维护方 → 审核并在当前 main 更新 Skill → 专家在安全停点采用新版`。未发布续建沿同一开发流程接首个未放行节点，旧 `migration` 只作历史来源标记；只了解 Skill 时不假定已有 Agent、平台账号或发布结果。已取得具体项目材料时，改用下述当前项目路线，标出已证实、当前门禁与下一步，不机械重复通用总览。

首次进入具体 Agent 工作时，Codex 依据当前模式和范围给出一份简短路线：现有材料与基线、目标平台合同与适配、适用测试、制包发布、真实使用与更新，标明已证实、当前门禁和后续待做；不适用的段落省略，不把路线图当成已完成证据。此后只更新发生变化的节点。每次用当前项目证据和目标实例正式材料确定下一个未证实环节，已有证据直接复用。对已授权且工具可执行的动作，先执行再报告结果，不把查文件、运行校验、诊断或编写项目内记录转交给开发方。结果回来后立即判断放行、修复、补证、归属待核或继续下一适用节点，不让开发方凭 Node 名称自行猜下一步。只有缺少开发方独占的业务决定、原材料、客户端观察或必要认证时，才一次问一项准确输入，并说明得到后将执行什么；等待时继续无依赖工作。

把 Node 0–8 当作开发方可见的大节点，而不只是项目内检查点。进入项目时按当前流程列出适用节点的通俗名称和 `已证实/当前/待做/不适用` 状态；利用另一项目材料时先标保护原件与建立副本，未发布续建接已有停点，优化只列受影响节点。每个适用节点开始时说明本节点要达成什么、Codex 此刻做什么及通过条件；完成、阻断、重开或转入下一节点时更新状态，指出下一动作和执行者。多个相邻节点在一轮内完成时合并成一条进度消息，逐项标出结果；无需逐个工具调用或字段解释。发布后的真实试跑、故障分流与专家更新也按同样方式引导。不能只在首次展示总览，此后让开发方自行推断进度。

项目路线使用下列通俗名称，并按本项目实际证据标状态；不要把细项展开成教程：

| 大节点 | 对开发方显示的名称 |
| --- | --- |
| 入口 | 确认目标与现有材料；借用另一项目材料时保护原件、建立副本 |
| Node 0 | 明确本轮需求与范围 |
| Node 1 | 盘点运行环境与依赖 |
| Node 2 | 对照原业务流程与 DClaw 流程 |
| Node 3 | 确定专家、平台和本地助手各自负责什么 |
| Node 4 | 对齐交互、状态与接口合同 |
| Node 5 | 实现适配 |
| Node 6 | 测试与验收本次实际使用的能力 |
| Node 7 | 构建签名包并独立验签 |
| Node 8 | 上传、激活并回读 |
| 发布后 | 真实试跑、故障处理与下一版更新 |

展示时用 `已证实 / 当前 / 待做 / 阻断 / 不适用` 标记。未发布续建按 `new-development` 从第一个未放行或受影响节点接上；旧 `migration` 记录不改写，只作为来源说明，不要求从头重走。已发布优化只显示本次受影响的节点、必要回归和发布后验证。每次节点变化只需一句简短进度：`当前：<节点与状态>；我正在/已完成：<动作与结果>；下一步：<节点、执行者、通过条件>`。无项目时仅展示通用路线，不给尚不存在的项目填写虚构状态。

对外说明保持简短且具体：`当前已证实什么 | 我现在完成或正在执行什么 | 下一门禁及通过条件 | 仅在必要时需要开发方提供什么`。不要只复述整套流程或把门禁错误转成泛泛的“补完整项目/做全量测试/联系平台”；应先按相应模式和正式合同完成权限内的核查与最小修复。每个节点结束或受阻后更新项目停点，并按[卡点回传与每日补漏](blocker-feedback.md)留证，下一轮从该停点续接。只安装了解 Skill 时完成安装和发现验证，展示上述总览并说明如何开始具体项目，不强行启动 Agent 节点。

## 先确定当前停点

从项目现有记录和目标实例正式回执核对：当前模式与发布范围、Skill 版本、适用 Node、最近一次已证实结果、当前签名包及激活 Release、失败回合实际 Release（若有）、尚未通过的下一项门禁、待回复事项及其状态。当前列表回读只证明查询时的激活版；截图、模型自述、离线测试和平台口头结论各按其证据范围使用。不要让用户重新提供项目里已有的任务 ID、回执或决定。

在项目已有进度或交接记录中维护一处简短停点：`已证实结果 | 下一门禁 | 下一动作与执行者 | 依赖/待回复 | 证据位置`。平台请求已由转交人发送时，核对实际发送的文件或内容、可得的摘要与发送依据；同名本地草稿不能代替已发送原件，用户确认发送也不等于平台已接单。只在结果、归属、依赖或下一动作变化时更新；不要为每轮普通回复另造报告。新对话先读这处停点，再回读容易变化的平台状态。

每个适用 Node 完成、阻断或因新证据改变结论时，在同一项目停点补一条短检查点：`模式/Node | Skill 版本 | Agent 版本与 Release（若有） | 正式合同版本 | 结果及证据位置 | 三类能力实际使用和 E2E 状态 | 未解决项/下一节点`。独立总控、发布者或接入方法维护方参与项目时，按已授权渠道发送脱敏检查点并记录“待发送/已发送待审核/已审核”及对方结论；没有跨对话工具时留待办，恢复可用后补发。接收方逐节点判断项目问题、平台问题、通用 Skill 缺口或证据不足；即使不改共享 Skill，也回传“已审核、无共享改动”。实际卡住的每个子步骤另按[卡点回传与每日补漏](blocker-feedback.md)留证，并将可安全共享的摘要交本工作区维护方；普通顺利节点不建卡点，客户内容、签名包和原始回执不进入共享 Skill。

平台最终回执到达时，先在当前 Agent 项目核对与复测，立即更新原卡点，判断是否产生可复用的接入知识；等待平台或维护方处理期间继续无依赖工作。反馈补漏从当前项目上次成功巡检时间起，逐项核对实际步骤中的卡点、项目检查点和最终回执；按项目卡点编号去重，巡检时间和待办留在项目现有进度记录中。未取得的材料写未核，不补造回执；仅属 Agent 业务的卡点也可脱敏交维护方审核归属，但不把业务规则改成通用 Skill。

## 按结果选动作

| 当前事实 | 下一动作 |
| --- | --- |
| 新 `super_expert_public` 的静态校验因缺 `signer_id` 失败，尚未签名上传 | 先核本轮已批准的发布范围和新 `agent_id`，再按目标正式 DevKit 用当前普通开发账号在本机 `keygen`、`publish register-signer`，把账号绑定的 `signer_id` 写入 manifest；随后对冻结输入运行正式 `digest → validate → test → build → verify`。注册、身份或权限失败时保留准确回执并仅阻断对应节点，不停在“缺 signer_id”而不执行可做的登记。属于本轮发布范围的卡片、AIGC 和失败恢复须完成发布前合同及受控测试；真实客户端续接在激活后验收。门禁通过且取得本次公开发布授权后再 `publish upload`、`publish list`。 |
| 使用来源材料开发时 `validate/test` 报 `behavior_baseline` 缺失或未验证 | 先核实际命令与报错来源、来源材料、本轮范围、现有测试及其与来源修订的对应关系，再查项目自检或当次正式 Pack/DevKit 对字段和证据的要求；有效测试直接映射，缺的只补最小必要记录与验证，在副本修正后重跑对应门禁。静态校验或测试数量不等于该字段已通过。执行后仍失败才报告准确缺口；不预设旧签名包或固定全量用例。详见[统一开发流程](new-development.md)。 |
| 私有能力包缺客户网络可访问的正式 HTTPS artifact 地址 | 开发方先落实其控制的托管地址，上传确定性制品并核对大小、SHA-256，以及资源锁和签名描述符各自对下载主机的允许域要求，再生成签名描述符和运行 `capability-build/build`。平台负责 signer 信任、能力注册与安装授权；不要把平台未提供私有托管入口直接归为平台缺口，也不以 `.invalid` 或临时 URL 冒充门禁通过。 |
| AIGC 工作流未结束，但客户要使用已成功节点的资产 | 先查目标实例正式合同是否允许在进行中按节点读取可信资产并交给下游，核对成功 job、资产来源、当前任务版本和授权；不能从客户端“已完成”或快照 Schema 的可空字段推定可用。若合同只覆盖已提交产物，停止这条下游路径并请求明确的部分节点读取与资源交接合同，其他节点按原工作流继续。 |
| AIGC 资产要直接进入本地助手，但只有资产 ID 或本地文件选择引用 | 按最新正式合同核对上游任务/节点状态与资产来源；目标实例提供 `aigc.task.assets.localize/1` 时，Agent 读取同任务资产清单并提交选定资产计划，由 Host 预检公开 OSS 地址并派发给助手，不要求 Agent 自行取得 URL。资产 ID 不等于设备 `local_file_ref`；客户手动下载后再选文件属于不同路径，不能冒充 Host 本地化通过。只有目标实例确无适用正式合同，才保留上游资产并记录公共能力缺口。 |
| 官方 Pack 包装器拒绝标准与 DevKit 列出的真实能力声明 | 保存同一次正式材料的版本、项目声明、包装器错误及独立 DevKit 结果；先排除声明与项目记录不一致。若标准明确允许独立 DevKit 路径，按冻结输入完成正式四步并用服务端回执、列表回读核对发布状态，包装器失败另报平台澄清；独立路径无正式依据或自身门禁未过时阻断受影响发布。不改官方包、不删真实声明或填占位制品绕过。 |
| 未选模式或尚无业务基线 | 先读当前项目；已知模式直接进入适用 Node，只问材料无法确定且会改变流程的第一项问题。回答一到就记入项目并继续，不重复整套问卷。 |
| 某节点的合同、实现或测试未通过 | Codex 先完成权限内能做的核查、修复和定向验证；依据影响范围回到相应 Node。只挂起依赖缺口的链路，继续不依赖它的工作。涉及发布范围删减时按模式取得具体批准并重核门禁。 |
| 正式合同或官方示例允许某能力路径，但 Skill 规则阻断或增加无关步骤 | 核对同一目标实例、能力版本、账号权限、输入范围和结果层级，找出 Skill 多加的条件及其依据。正式材料足以证明允许、尚无真实成功回执时记“合同允许、运行未验证”；记录卡点并脱敏回传维护方，按合同继续已授权且满足原副作用门禁的工作。项目自设或正式合同要求的限制继续执行；证据不足标待核。不得误报平台缺能力，也不得用重复收费调用证明 Skill 问题；真实调用、签名、授权及发布各自验收。 |
| 平台交接了新流程或源码版本，但目标实例尚未开放正式包与 Schema | 分开记录交接中的目标设计和当前认证回读的生产合同，保留现有激活 Release。先在独立草稿实现并测试不依赖新合同的部分；涉及未公开请求形状、授权和真实调用的接线保持阻断，不凭交接文字或平台源码猜参数。目标实例正式发布后再认证下载、核对版本与 Schema，完成接线、受影响节点回归和本次发布门禁。 |
| 新流程标准已在目标实例发布，但所需 Host 请求/响应合同仍未公开 | 核对认证 Pack、DevKit 的请求/响应 Schema、操作目录，以及正式标准、示例附带说明和实时目录提供的失败语义；有独立错误 Schema 时一并核对。能力 ID、流程文字或回执 Schema 不足以确定可编码请求，单独缺少错误 Schema 文件也不等于请求/响应合同缺失。保留已激活版，在独立草稿继续业务候选、状态与校验等不依赖缺失合同的工作；请求/响应或必要失败关闭语义仍不足时，将受影响的 Node 4 接线和后续真实调用、密封发布门禁标为阻断，准确记录缺口。取得正式合同后再补接线、测试与发布，不用旧兼容路径冒充新标准已完成。 |
| 正式能力已提供，但当前已签名包未声明 | 先确认该能力是否属于本轮发布范围。属于时，按当前 Agent 的 Node 3/4 补实际接线与声明，完成受影响的 Node 6/7/8 门禁并发布新版本，再用新 Release 验证真实调用；仅有本地草稿或平台能力目录不能让旧 Release 使用它。不属于时记为不适用，不要求客户试用，也不据此报告平台缺能力。 |
| 已签名包声明能力，但当前安装未获授权 | 先核对本次 Release 的正式上传、安装与授权回执及目标实例合同；分清 Agent 声明/发布输入错误与平台授权失败，按归属回到相应节点。授权未证实前不让客户测试该能力，也不把平台目录可见当作本安装可调用。 |
| AIGC 工作流卡已打开，但下游缺可信任务或资产 | 先核对当前 Release 的声明、安装授权和已保存的 `material_task_id`；有正式开发者只读查询时，核对原会话是否已有唯一任务，旧 `task_key` 不可核就不加键过滤，不把查询结果自动写入 Agent。目标提供 `aigc.task.binding.resolve/1` 且项目需要恢复时，由新签名版声明并获授权，在原会话用可信旧键过滤或空请求唯一匹配；从创建尝试或已存绑定定位原任务的历史作品修订，不以当前 `latest` 代替，再核对 Host 回执修订、同 ID 快照与非空画布。客户点击或画布可见只算导航证据；过滤 `not_found` 不排除其他旧任务，无唯一绑定、授权或原始回读时停止下游及重复创建，按证据处理 Agent 接线或平台合同/执行缺口。 |
| 本地任务所需能力包尚未正式登记或授权 | 开发者先按目标正式材料核对 Component 与私有能力输入，准备独立签名的能力包和可核验摘要；按正式流程交由有权限的管理员登记 signer、公钥和描述符，取得注册表与安装授权回执后，按目标实例正式入口取得准确能力版本的设备 `ready`，再接 `local.task.start/1`、`local.task.read/1` 并验客户本地产物。普通专家发布权限不能代替能力包登记；登记、授权或设备准备缺失时仅挂起该本地链路，继续其他独立工作。 |
| 发布已激活，但真实能力尚未验收 | 先核对本次 Release 与安装授权，再沿当前项目自然业务路径验证**下一个未证实环节**。建卡、提交、可信读卡；工作流创建、适用的任务或节点状态、资产；本地任务受理、执行、产物分别推进，已有证据不重测。需要人操作时给一条准确操作、预期观察和停止条件；不让客户手动完成本应由 Agent 发起的工具调用。 |
| 客户端或平台能力报错 | 执行 [故障分流](runtime-feedback.md)：保留现场，查失败时 Release、首错与最终阻断、正式合同和项目实现。能在开发侧修的直接修并复测；证据不足标“未归因”，列出能改变归属的下一份证据及取得者，不以通用错误提示猜平台责任。 |
| 平台请求已备但未转交 | 标为“待转交”，不给它写“平台正在处理”。由既定转交人决定发送；Codex 继续不依赖回复的工作，不重复生成新请求。 |
| 平台请求已转交、待回复 | 保留主题、回传位置和依赖节点；只暂停受影响或可能重复收费、提交、污染状态的动作。用户明确要求先等本次回复时遵守该顺序；其余独立工作可继续。 |
| 已转交请求等待期间出现新证据 | 先对照实际已发送内容，记录新证据及其是否改变原请求的定位、修复范围或时效。能在原任务最终回执中核对的先留在项目，继续独立工作；确需补充时形成同一任务的精简增量及原因，经既定转交方式处理，不把新草稿当成已发送，也不要求重复发送整包。 |
| 收到平台中间或最终回复 | 对照原请求逐项核对正式合同、部署/发布版本、回执和未解决项。中间进度不结案；证据齐备就更新受影响 Node 并恢复原任务，缺关键字段时形成一次具体补齐请求，不让转交人往返查内部日志。 |
| 新反馈只影响某专家业务，或暴露可复用工具缺口 | 先在 Agent 项目处理或定位卡点，并按脱敏规则交本工作区维护方审核；后者若确属通用缺口才改共享 Skill。维护者按 README 的审核流程处理；收到、审核、修复、提交和专家采用分别记录。 |

每次给用户回复时，先执行已授权且 Codex 自己能完成的下一动作，再简短说明**已证实到哪、现在由谁做哪一步、收到什么结果后怎样继续**。用户只需提供确实缺失的业务决定、客户端观察或其独占材料；不要用“继续测试”“联系平台”“等回传”代替一条可执行的下一步。若当前确实只能等待，指出具体待回复事项和不受它影响的可做工作。一次操作的结果回来后重新按本表判断，不沿用已撤回的旧指令。
