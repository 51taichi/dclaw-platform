# 从零开发模式

本文件用于所有未首次发布专家的 `new-development`，包括从需求起步、使用现有材料和旧记录标为 `migration` 的项目续建。先读取主 `SKILL.md`；公共 Component、职责边界、平台确认、密封和发布门禁继续有效。旧项目的历史模式字段不改写，当前节点记录标明按本版统一流程续接。

“从零”指每个新专家从自己的 Node 0 范围和 Node 1–8 门禁开始，不要求代码从空目录写起。开发方可只借用旧代码结构，也可声明沿用已有业务行为；Codex 只确认两者的实际差异，不再要求选“新建或移植”。借用另一项目的旧包时，其 `agent_id`、能力声明、测试和发布证据不自动成为新专家的验收结果，原包不进入本 Skill 仓库；续建当前同一未发布项目则保留仍有效的身份与证据。

## 使用现有材料起步

来源可为仓库、本地工程、ZIP、平台导出包或部分源码与说明，不要求原项目完整、能运行、已签名或有历史测试。先只读确认候选来源、身份、可取得的版本、文件与摘要、代码、说明、测试和发布证据；多份候选且目标不明时才问选哪份。借用另一项目时，原件及已安装的本 Skill 留在工作副本之外；固定仓库修订，ZIP/导出包保留原件，在独立目录安全解包，复制本轮获准使用的材料并核对副本清单、复制前后原件摘要。续建当前同一未发布项目时沿用其现有工作区和证据，不为改模式再复制一次。旧源项目之后独立变化时按新时间点记录，不倒推为本轮复制所致。凭据、缓存和私钥不复制进发布物。

在本轮工作区的 Node 0 标注是“沿用已有业务行为”还是“只借用实现参考”，以及逐项纳入、改变或暂不纳入的范围；只需确认会影响范围和验收的差异，不要求原项目先补完。沿用的可证实行为作为本轮约束，未验证或未实现的行为如实标记；删减或改变已确认的范围内行为要逐项批准。只借结构时按新需求定义业务，不把旧行为自动变成要求。仅有 `agent/` 运行快照可以作为有限开发输入，缺少构建材料时补齐；改 `agent_id` 或重压 ZIP 不能代替正式构建。

Node 6 先将现有测试映射到来源修订、本轮范围、输入预期与实际结果；有效证据直接复用，关键路径缺失时只补最小必要验证。来源与目标均可执行时用相同输入对照；来源无法运行时把等价性标“待证”，不把说明或静态工具通过称为业务等价。`validate/test` 报 `behavior_baseline` 缺失或未验证时，先确认错误来自项目自检还是正式 Pack/DevKit，查当次 Schema、命令帮助、项目证据和完整错误回执；把有效测试映射到要求的字段，只补缺失记录后重跑。仍失败才报告准确缺口，不先索要旧签名包或自行设定固定数量的全量用例。

起步时取得并校验目标 DClaw 当前的 Developer Pack、DevKit、完整 Registry 和版本回执。新项目从第一版就按这些正式合同设计；Node 0 确认业务需求，Node 1 才判断每项需求对应的实际依赖与能力。材料暂缺时可做需求盘点，但不能把候选设计认定为已适配目标实例。

官方 `init` 生成的是待填写模板，不是已确认的 Node 0。`validate` 的第一条错误按 CLI 自身检查顺序返回，不能据此推断更早的需求、依赖或业务合同已通过；例如模板尚无业务基线时也可能先报缺 signer。Codex 按本 Skill 的 Node 顺序独立核对并记录缺口，签名登记留到 Node 7，不让早到的 CLI 错误改写当前业务澄清顺序。

## 执行顺序

```text
Node 0 需求基线
  -> Node 1 依赖环境盘点
  -> Node 2 业务基准与 DClaw 流程对照
  -> Node 3 职责与能力设计
  -> Node 4 卡片、状态机与接口合同
  -> Node 5 实现
  -> Node 6 测试与业务验收
  -> Node 7 密封与独立验签
  -> Node 8 上传、授权与激活
  -> 移交项目方客户验收
```

不得因为这是从零开发而跳过依赖、测试、密封、上传、授权或激活门禁。Node 8 后的正式客户验收由项目方自行执行，不属于本 Skill 节点。

## Node 0 输出

先整理已有材料，再列出真正影响业务流程或验收的待确认项。不要要求用户重复回答材料中已经给出的内容，也不要把所有可能的工程选项组成问卷。

### 0.1 事实来源

记录本轮使用的用户指令、业务文档、来源代码和测试、示例输入、示例产物及现有平台约束。每项结论标记来源：

- `confirmed`：用户已经明确确认；
- `evidence`：可以从材料直接证明；
- `unresolved`：现有信息无法确定，且会影响流程、依赖或验收。

按客户实际填写顺序列出，不使用内部编号代替字段名：

### 0.4 业务步骤

每个步骤必须足以供 Node 1 判断实际技术操作：

| 步骤 | 输入 | 业务处理 | 判断/分支 | 人工操作 | 输出 | 失败与重试 | 状态/证据 |
|---|---|---|---|---|---|---|---|

正常流程、可选流程、重试、恢复和人工复核都要列出。描述业务目标和事实，不在此处擅自决定平台模块、库或实现语言。
若业务分阶段产出，逐阶段列出用户何时需要选择、修改或确认，以及该决定影响的后续步骤；只把项目方或正式平台合同要求的确认列为正式推进门槛。

### 0.5 外部服务与本地重任务候选

| 业务步骤 | 第三方 API/账号候选 | 本地文件或重任务候选 | Secret/费用/时限约束 | 状态/证据 |
|---|---|---|---|---|

这里的“候选”只用于后续分类，不代表已经批准供应商、平台改造或本地助手依赖。

### 0.6 业务验收案例

| 案例 | 输入 | 预期业务结果 | 允许的人工操作 | 失败判据 | 费用/时长限制 | 状态/证据 |
|---|---|---|---|---|---|---|

至少要有能够证明核心业务目标的业务案例。没有真实账号或付费凭证时，可以完成不依赖它们的分析与实现，但受影响的 Node 6 测试必须记录为未完成，`e2e-verified` 保持 `false`，不能用模拟成功代替。

### 0.7 Node 0 放行

同时满足以下条件才进入 Node 1：

- 业务目标、输入、最终产物和完成判据明确；
- 每个业务步骤及其分支、人工操作和失败处理可追踪；
- 第三方服务和本地重任务候选已经暴露，没有隐藏链路；
- 至少一个业务验收案例能够判断成败；
- 剩余 `unresolved` 项不会改变业务流程、依赖分类或验收结论。

未满足时只集中询问会改变上述结论的事项。用户确认后更新同一份需求基线，不另建相互冲突的版本。

## Node 1 在从零开发中的执行方式

从 Node 0 的每个业务步骤出发，形成以下闭环：

```text
业务步骤/分支
  -> 必须完成的实际技术操作
  -> 运行位置（Agent、业务 API、本地助手）
  -> 依赖或远程合同
  -> 公共/私有分类
  -> Registry 和公开调用合同状态
```

不得为了使用注册表中已有 Component 而改变业务设计。也不得因为尚未编码就把下载、转码、识别、模型、浏览器或高资源任务排除在盘点外。

Node 1 仍使用主 Skill 的固定五列表和完整 Registry 门禁。任一所需公共依赖为 `reserved`、`absent` 或 `unverified` 时，受影响链路不能进入 Node 2 或本次发布门禁；不依赖该项的盘点、实现和离线测试可继续。若调整发布范围，先取得具体确认，再重新核对完整依赖。

## Node 2 在从零开发中的两张图

第一张图把 Node 0 已确认的业务步骤和卡片字段按真实顺序画出。第二张图使用相同编号，展示每一步由超级 Agent、业务服务、DClaw 通用能力或本地助手如何承载。

第二张图不得新增第一张图不存在的业务目标或客户步骤。纯技术动作可以作为对应业务步骤的内部承载显示，但必须能够回指业务步骤，并在 Node 3 和 Node 4 中形成公开合同。

## Node 3 至 Node 8 的节点证据

| 节点 | 必须保留的证据 | 放行条件 |
|---|---|---|
| Node 3 | 业务步骤到责任位置、能力、输入输出和失败归属的映射 | 没有未归属步骤；平台缺口已解决或受影响链路停止 |
| Node 4 | 卡片、状态机、API、本地任务、错误和交付合同 | 每个业务步骤都有可实现、可测试的正式合同 |
| Node 5 | 对应节点和合同的实现及版本记录 | 实现未超出需求基线，未绕过依赖或平台门禁 |
| Node 6 | 自动测试、合同测试和真实案例结果 | Node 0 的成功、失败与案例预期均有证据 |
| Node 7 | DevKit 来源与摘要、密封产物、签名和干净目录验签结果 | 密封包通过正式 DevKit 校验且不含禁止内容 |
| Node 8 | 上传、验签、授权、安装和激活的独立回执 | 当前版本已由目标实例激活；存在外部阻断时保持 Node 8 blocked |

Node 8 完成后，当前 Agent 开发者交付当前版本、上传/授权/激活回执、已知限制和回滚版本，并以 `e2e-verified=false / 待客户验收` 移交项目方。随后按[下一步决策与续接](next-step.md)跟踪本项目实际使用能力的真实验收；项目方或获授权的开发者可以提供客户端证据，不要求每个新开发者验证本 Skill 的全部三类代表能力。反馈问题先定位归属，再以新版本回退对应开发节点处理。

## 强制回退

- 发现需求或完成判据不明确：回退 Node 0。
- 发现新依赖、执行位置变化或 Component 合同缺失：回退 Node 1。
- 发现流程、字段或业务分支不一致：回退 Node 2。
- 发现职责归属或平台能力边界错误：回退 Node 3。
- 发现合同不足以实现或测试：回退 Node 4。
- 实现、测试、密封和真实运行不得用临时绕过代替回退。

回退只修改受影响节点及其后续证据，不得静默改写已经确认的需求基线。
